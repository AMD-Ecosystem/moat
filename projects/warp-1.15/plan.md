## How the 1.14 port is carried onto 1.15

**Recommendation: two merges, no rebase, no cherry-pick.** On `release/1.15.0.amd0` (today an exact copy of `release-1.15` at `ffa038b1`):

1. `git merge -s ours release-1.14` with a message saying that upstream's `release-1.14` is superseded by `release-1.15`. The merge commit's tree is byte-identical to `release-1.15` (checked in the trial: `git diff release-1.15 HEAD` is empty). It only records `release-1.14` as an ancestor.
2. `git merge release/1.14.0.amd0` (a real merge; the trial used tip `1c94e68b`). Because step 1 made `release-1.14` (`3601b2d0`) the merge base, git applies exactly the 1.14 port delta (`release-1.14..release/1.14.0.amd0`, 96 commits, 118 files, +4545/-550) onto 1.15, and nothing else.

Why step 1 is needed and is safe. `release-1.14` and `release-1.15` fork at `e8b905d7`; upstream keeps release branches apart and cherry-picks fixes between them. `release-1.14` carries 22 commits that are not ancestors of `release-1.15`: 15 are cherry-picks whose equivalents are on `release-1.15` (`git log --cherry-mark --left-only release-1.14...release-1.15` marks them `=`), and 7 exist only on 1.14 (`1a9906ad`, `c242c264`, `e265a974` version strings; `5a671c30`, `d23b3854`, `597b97d3` the 1.14 changelog, with docstring wording in `warp/_src/optim/linear.py` that 1.15 already has; `e70d9eca` APIC docs, whose 1.15 equivalent is `7a48201a`). None carries code 1.15 lacks. Without step 1 the merge base is `e8b905d7` and the merge replays those 22 upstream commits against 1.15's later edits of the same lines: the trial produced 45 conflicting files, 25 of them conflicts between two upstream versions of docs, ASV, APIC and `context.py` that have nothing to do with the port, mixed into the same files as the real port conflicts. With step 1 the trial produced 20 conflicting files, every one a genuine port-versus-1.15 conflict.

Why a merge and not the alternatives:
- Rebase or cherry-pick of the 96 commits onto 1.15 rewrites history: every conflict is met once per commit that touches the region (including commits later reverted, such as the speculative ray traversal and the 64 KiB sizing commits), the credit lines and evidence in the original commit bodies are copied rather than referenced, and a later 1.14 commit has no ancestry link, so nothing tells the 1.16 line which 1.14 fixes 1.15 already has.
- One squashed "port" commit loses the per-commit authorship credits (cuBQL backports crediting the upstream PR authors, the hunks credited to their AMD authors) and the per-commit rationale.
- A merge keeps the 1.14 commits as they were reviewed and validated, keeps attribution, and lets every later line repeat the same two steps (1.16 merges `release/1.15.0.amd0`).

How later 1.14 commits arrive (the Windows round, a gfx1250 rerun fix, any review fix): `git merge release/1.14.0.amd0` again. The previous merge is the base, so only the new commits' delta is applied. Two rules:
- If the 1.14 line later takes an upstream patch release (a sync round that merges a newer `release-1.14` tip into `release/1.14.0.amd0`), first repeat step 1 for that tip in the 1.15 branch, after checking with `git log --cherry-mark --left-only <new release-1.14>...release-1.15` that every non-version commit in it is already on `release-1.15` or is 1.14-only; a fix that 1.15 lacks is a question for jeff, not something the merge silently brings in.
- A 1.14 commit that only reverts or rewrites something 1.15 resolved differently in its merge is still merged (history stays complete) and its resolution is recorded in the merge commit body.

The merge commits are upstream-visible fork history: titles of at most 72 characters, no `[ROCm]` prefix unless the resolution itself adds HIP code (it usually does for step 2, so `[ROCm] Merge the 1.14 HIP port into 1.15` is the expected shape), a body listing each conflicted file and how it was resolved, the AI-assistance disclosure, and a Test Plan. `jargon.py --port warp-1.15` scans every commit in `release-1.15..release/1.15.0.amd0`, which after step 1 includes upstream's 22 `release-1.14` commits; if it flags upstream's own wording there, that is upstream text and not ours (record it in notes, as LichtFeld-Studio did), but our own merge messages must be clean.

## What upstream changed in 1.14..1.15 that needs porter work

Line numbers are on `release-1.15` unless marked. Each item names its `surface.json` id. "Port rule" means the 1.14 design rule that decides the handling.

### A. Device code in runtime-compiled kernels (headers every generated kernel includes)

Under hipRTC the port defines `__CUDA_ARCH__` to `1` (port `warp.cu:4590-4593`), so every new boolean `#ifdef __CUDA_ARCH__` in a header is true there and every numeric `>= N` false; under the AOT hipcc build neither is defined. HIP's `__shfl*_sync`/`__ballot_sync` `static_assert` a 64-bit mask (`hip/amd_detail/amd_warp_sync_functions.h:177-215`), so a 32-bit mask is a compile error, not only a wrong mask.

1. **`deterministic.h` (new, included by every generated kernel, `codegen.py:5772,5794`)** -- `device:ptx-inline-asm`, `runtime:device-compile-predicate`, `feature:deterministic-mode`.
   - `is_global_store_target` (`:235-243`): `#ifdef __CUDA_ARCH__` then `#if defined(__clang__)` selects inline PTX `isspacep.global` with an `"l"` constraint; otherwise `__isGlobal`, which HIP does not have. Under hipRTC the PTX branch is taken, so every kernel can fail to compile. Needs a HIP branch first: not shared and not private (`__builtin_amdgcn_is_shared` / `__builtin_amdgcn_is_private` on a generic pointer, the form HIP's own `amd_hip_cooperative_groups_memcpy.h` uses; porter verifies). This is the first thing to fix after the merge: until it is fixed no HIP kernel may compile.
   - Six boolean gates (`:62, 85, 147, 216, 235, 289`; macro block `:289-326`) protecting device `atomicAdd(int*)`, `atomicCAS(int*, 0, 1)`, `printf` and the `WP_DET_*` macros: widen to `defined(__CUDA_ARCH__) || defined(__HIP_DEVICE_COMPILE__)` (port rule), otherwise an AOT HIP device pass would silently take the CPU macros.
2. **`tile_reduce.h`** -- `device:tile-wavefront-width`.
   - New non-template `half`/`bfloat16` `warp_shuffle_down(val, int offset, int mask)` overloads (`:35-55`), and new overloads for `vec<half>`/`vec<bfloat16>` (`:99,112`), `mat<half>`/`mat<bfloat16>` (`:138,152`), `T*` (`:165`), `shape_t` (`:176`), `array_t` (`:186`), `indexedarray_t` (`:205`), all with `int mask`. Change every one to `tile_mask_t mask` (the port's 64-bit HIP mask type). With `int`, the non-template ones fail HIP's static_assert and overload resolution would route a `tile_mask_t` argument to the generic template instead. Shuffling 16-bit values through `unsigned int` is fine on HIP; widths already use `WP_TILE_WARP_SIZE`.
   - Generic `warp_shuffle_down` (`:57`) rewritten from a union to an `alignas` word buffer: take upstream's body with the port's `tile_mask_t` signature (merge conflict above).
   - `warp_reduce`, `__ffs`, `1 <<`, `__ballot_sync(0xFFFFFFFF)` (`:218-505`) unchanged upstream; the port's hunks apply.
3. **`tile_radix_sort.h`** -- `device:tile-wavefront-width`.
   - New `warp_shuffle_xor` family (`:102-271`) hard-codes `__shfl_xor_sync(0xFFFFFFFFu, ...)` at `:105, 116, 144, 156, 192, 229, 230, 240, 253, 254, 255`; the `half`, `bfloat16` and `shape_t` overloads are non-templates and always compiled. Replace with `WP_TILE_SYNC_MASK` (or a `tile_mask_t` parameter). The xor stride stays below 32, so the default width keeps it inside a 32-lane group on wave64, as the port's existing bitonic code assumes.
   - `codegen.py:5926,6274,6289` emits struct `warp_shuffle_xor` per field under `#if defined(__CUDA_ARCH__)`; it calls the native helpers, so fixing the helpers covers it. The tile sort of struct and bf16 payloads (`test_tile_struct.py`, `test_tile_sort.py` bf16 case) exercises it.
   - `FloatKeyToUint::convert` (`:42`) new `#if defined(__CUDA_ARCH__)` choosing `__float_as_uint`: correct either way, widen for consistency (port rule).
4. **`builtin.h`** -- `runtime:device-compile-predicate`. `atomic_cas`/`atomic_exch` bodies for float/double/int64 now use `__float_as_uint`/`__double_as_longlong` and friends (`:2421-2505`); take them under the port's widened predicate (merge conflict above). Plain 32/64-bit CAS/exch, within the safe-forms ruling.
5. **`texture.h`** -- `feature:texture-mipmaps`, `feature:device-textures`.
   - Every sampler takes `lod` and calls `tex1DLod/tex2DLod/tex3DLod` when `lod >= 0` (`:687-858`): under the port's `WP_TEXTURE_HW_SAMPLING[_3D]` and `WP_TEXTURE_OBJECT(...)` (HIP has the `*Lod` forms for `hipTextureObject_t`). The new Clang-CUDA stubs (`:659-673`) gain the `*Lod` stubs; keep the port's macro block after them.
   - The `Texture` struct is rebuilt (`:60-150`): one constructor `(ndim, num_mip_levels, mip_widths, ..., mip_filter_mode, ...)` replaces the three per-dimension ones; new members `mip_data[16]`, `mip_offsets[16]`, `mip_{widths,heights,depths}_arr[16]`, `num_mip_levels`, `mip_filter_mode`. The software sampler (`cpu_sample_*`, which the port's no-image path runs on the GPU) now reads `mip_data[level]` and `mip_*_arr[level]` even for level 0. So the port's `texture_software.cpp` (port `:139-158`, `wp::Texture desc(1, ...)` and patching only `data`/`width`) no longer compiles, and patching only `data` would leave the device reading host `mip_data` pointers. It must build the device descriptor with the unified constructor, set `mip_data[l] = device_base + mip_offsets[l]` for every level, copy the per-level arrays, and take `num_mip_levels` and `mip_filter_mode` through `wp_texture_software_create`/`_object_create` to match the new `wp_texture_create_device`/`wp_texture_object_create_device` signatures. This is mandatory even with mipmaps refused: gfx942/gfx950 sample every texture in software, gfx90a its 3D textures. The rest of the mipmap scope is Q3.
6. **`mesh.h`, `intersect.h`, `bvh.h`** -- `feature:bvh-mesh-hashgrid`.

## Risk list

1. **A clean merge that is semantically wrong.** The 32-bit mask code in `tile_radix_sort.h`, `tile_reduce.h`, `sparse.cu`, the PTX in `deterministic.h` and the arch-90 cluster gates all merge without a conflict. The first HIP build after the merge is expected to fail to compile; the porter fixes those before anything else, then sweeps the whole merged tree with the three patterns 1.14 used (32-bit literals with `*_sync`/`__ballot`, `1 <<` lane shifts, `__popc`/`__ffs` on masks) including vendored subtrees.
2. **The software texture sampler** must be rebuilt for the new `Texture` struct even before any mipmap decision; it is the only texture path on gfx942/gfx950.
3. **cuBQL trees under the HIP depth-level refit** read uninitialised `node_counts` (B.5).
4. **Determinism on rocPRIM** (B.3): the mode's run-to-run promise depends on a deterministic reduce-by-key on HIP.
5. **Int-arch decisions on HIP devices**: clusters (`>= 90`), the deterministic tests' bf16 choice (`>= 80`), and `context.py:5146`'s arch-suffix check; any new Python path keyed on `Device.arch` gets an explicit HIP decision.
6. **Ray traversal and contraction** (A.6): exact `t` comparisons without padding and a doubled per-thread stack in hipRTC kernels; consistency scripts and timing on gfx90a/gfx942/gfx1100.
7. **New hipCUB surfaces** (in-place `DeviceSelect`, 128-byte proxy values, rocThrust iterators beside hipCUB, user-chosen sort bit ranges) with no previous Warp use on ROCm.
8. **HIP grid limits** in new raw launches (`sparse.cu`), and stale last errors after a failed raw launch before a hipCUB call.
9. **Windows**: hipMipmappedArray is not implemented on Windows per HIP's own header; 1.15's vcvars rework touches the path the clang-cl branch uses; the 1.14 Windows round is not done yet, so 1.15's Windows phase starts only after 1.14's Windows commits are merged in.
10. **The 1.14 head may still move** (Windows round, gfx1250 rerun, review fixes). Each move is merged forward; the porter records which 1.14 head each 1.15 merge brought in.

## Open questions for jeff

Six questions, none ruled. Q1 blocks the porter's first step; Q2 to Q5 block only the phases named; Q6 only the release. So the stage stays `planning` until Q1 is ruled. The porter does not start before warp-1.14 passes Linux revalidation at its final head in any case.

Q1. **How the 1.14 port is carried onto 1.15** (blocks Phase 0). Options: (a) two merges: `git merge -s ours release-1.14` (records upstream's 1.14 branch as superseded by 1.15, tree unchanged, verified byte-identical to `release-1.15` in the trial), then `git merge release/1.14.0.amd0`; later 1.14 commits arrive as further merges; (b) one plain merge of `release/1.14.0.amd0`, resolving all 45 conflicting files, 25 of them conflicts between upstream's own 1.14 and 1.15 versions of docs, ASV, APIC and `context.py`; (c) rebase or cherry-pick the 96 port commits onto 1.15 (history rewritten, no ancestry for later 1.14 commits); (d) one squashed port commit (loses per-commit credit lines and rationale). Recommendation: (a). It leaves exactly the 20 port-versus-1.15 conflicts, keeps every 1.14 commit as reviewed and validated with its attribution, and every later line repeats the same two steps. The cost is that the review PR's commit list also shows upstream's 22 `release-1.14` commits (its diff does not, since the merge base with `release-1.15` is `release-1.15` itself), and `jargon.py --port` scans their messages too.

Q2. **Thread block clusters on AMD GPUs** (blocks Phase 1's cluster work). 1.15 adds `cluster_dim` and keys every cluster decision on `Device.arch >= 90`, which every AMD GPU satisfies, while hipRTC drops the attribute, so today the port would report clusters active and run kernels unclustered. ROCm 10.x exposes cluster launch for gfx1250 only (`hipLaunchAttributeClusterDimension`, `hipDeviceProp_t.clusterLaunch`, runtime-only `hipOccupancyMaxActiveClusters`); no other AMD target has clusters. Options: (a) unsupported by capability on HIP, the way upstream treats pre-sm_90 NVIDIA GPUs: `cluster_dim` reported "ignored" with upstream's warning, `get_cuda_max_cluster_dim()` returns 1, the native cluster calls are no-ops and the launch uses `cluster_dim = 1`; `test_cluster_dim.py` selects devices by a capability, not by `arch`, so it runs its "ignored" cases on HIP; register a deferred item for gfx1250 cluster support; (b) implement clusters on gfx1250 in this line (needs device intrinsics in place of the PTX `%cluster_ctarank` probe, and the gfx1250 host, which is not ours at present); (c) raise an error on HIP whenever `cluster_dim > 1`. Recommendation: (a), matching what upstream already does on older NVIDIA GPUs, with the deferral.

Q3. **Mipmapped textures** (blocks Phase 3's mipmap part; the descriptor rebuild for the new `Texture` struct is owed regardless). Upstream marks mipmaps experimental. HIP has `hipMipmappedArray*` and `tex*DLod`, but its header says the mipmapped-array API is implemented on Linux and still under development on Windows, and gfx942/gfx950 (all textures) and gfx90a (3D textures) sample in software. The software sampler already implements LOD and mip filtering (it is upstream's CPU sampler running on the GPU), so serving mipmaps there needs storage for the extra levels, not new sampling code. Options: (a) hardware mipmapped arrays on Linux devices with image support; the software sampler with mip levels on devices without it (and gfx90a 3D); on Windows, try `hipMipmappedArray` on gfx1151 and route to the software sampler if it fails; (b) as (a) but always the software sampler on Windows, without trying; (c) refuse mipmapped textures (`num_mip_levels > 1`) on every HIP device with a clear error, release-note it, defer. Recommendation: (a): the same principle as the 1.14 texture ruling (GPU software sampling rather than refusal), little new code, and the six mipmap tests then run on every AMD GPU against Warp's CPU result.

Q4. **The optional CMake build on ROCm** (blocks Phase 6 only). 1.15 documents `cmake -S . -B _build/cmake -G Ninja` as an alternate developer build; upstream says release builds use `build_lib.py`. It is CUDA/CPU only and on a ROCm-only host fails at CUDA language enablement. Options: (a) add a HIP branch in this line (`WARP_ENABLE_HIP` or auto-detection mirroring `build_lib.py`: HIP language, `hip_compat.h` include, `warp/native/hip` shims, `amdhip64`/`hiprtc`, `texture_software.cpp`, the `.rocm` marker; Linux and Windows), more diff carried into 1.16 onward as upstream evolves the file; (b) no HIP branch: on a host with ROCm and no CUDA Toolkit the CMake build stops at configure with a message that says ROCm builds use `build_lib.py`, the install docs say the same, and a deferred item records CMake HIP support; (c) leave upstream's behaviour (a CUDA configure error on a ROCm host). Recommendation: (b) for this line. The documented ROCm build command (`build_lib.py`) just works and produces the release wheel; (b) turns the CMake path's failure into a clear, documented one with about ten lines of CMake, where (a) adds a second HIP build system to carry into every later line. If jeff reads the "documented build must just work" ruling as covering the alternate CMake path, the answer is (a).

Q5. **`radix_sort_pairs` with a bit range ending at bit 64 on 64-bit keys** (blocks Phase 2's sort work). 1.15 lets users pass `begin_bit`/`end_bit` (`wp.utils.radix_sort_pairs`) and adds `int64`, `uint64` and `double` keys. rocPRIM sorts such keys wrongly when `begin_bit > 0` and `end_bit == 64` (the defect 1.14 filed, `rocprim-radix-sort-u64-end-bit-64`); 1.14 only hit it internally and sorted all 64 bits, which is not equivalent for a user-chosen range because it reorders keys that tie on the selected bits. Options: (a) HIP-only workaround in `sort.cu`: for that case, sort a shifted copy of the keys (`key >> begin_bit`, a [0, 64 - begin_bit) range, which rocPRIM handles) with an index payload and gather, keeping the sort stable; plus a test of that range on every key type; (b) refuse that range on HIP with a clear error naming the ROCm defect, and a known-issue entry; (c) leave it (silently wrong results). Recommendation: (a), measured for cost against the full-range sort; it is the only option that gives users the result CUDA gives, and it disappears once the ROCm fix ships (the workaround is gated on the HIP build and documented with the report). If the porter finds it is more than a small change, bring (b) back to jeff with the size.

Q6. **Does the gfx1250 hold apply to 1.15's release?** (blocks only the release). jeff ruled on 2026-11-24 that the 1.14 release waits for one gfx1250 rerun at its final head, strict mode included, once that host is ours again. 1.15's wheels list the same 26 targets including `gfx1250` and `gfx1250-strict`. Options: (a) the same hold for 1.15: no 1.15 release until a gfx1250 run at its final head; (b) 1.15 releases with gfx1250 named "built, not validated on hardware" if the host is still unavailable then; (c) decide when 1.15 nears release. Recommendation: (a), for the same reason as 1.14 (the target ships in the wheel), noting that one host session could then cover both lines' final heads.
