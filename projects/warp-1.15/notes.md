## Lesson for cuda-to-rocm: hipMallocAsync is refused on every stream while a blocking stream is captured
Reference file: `references/faults-memory-streams.md` (graph capture). Symptom: `hipMallocAsync` on a stream that is not being captured returns `hipErrorStreamCaptureUnsupported` (900, "operation not permitted when stream is capturing") while another stream is capturing a graph. Cause: on HIP 7.17 (ROCm 10.2, MI300X), whenever the capturing stream is a blocking stream (created without `hipStreamNonBlocking`), stream-ordered allocation is refused on every other stream, blocking or non-blocking, for every capture mode (global, thread-local, relaxed) and with the thread's mode exchanged to relaxed; with a non-blocking capturing stream it succeeds, and plain `hipMalloc` succeeds in all cases. CUDA allows the stream-ordered allocation on an uncaptured stream there, which is what a "relaxed mode, allocate on a side stream during capture" pattern relies on. Fix: allocate such buffers with `hipMalloc` (in a pooled-allocator design, turn the pool off around that scope) on HIP. Reproducer (begin a thread-local capture on a default-flag stream, then `hipMallocAsync` on a second stream) in the warp-1.15 port's notes. (warp-1.15, 2026-11-25)

## Lesson for cuda-to-rocm: rocPRIM's reduce_by_key is not run-to-run reproducible for floating point; hipCUB's ReduceByKey inherits that
Reference file: `references/libraries.md` (Thrust/CUB). hipCUB's `DeviceReduce::ReduceByKey` calls `rocprim::reduce_by_key`, whose documentation says floating-point results may differ from run to run and points to `rocprim::deterministic_reduce_by_key` (same arguments as `reduce_by_key`). Code that relies on CUB's ReduceByKey being reproducible (a "deterministic mode", a bit-exact test) must call the deterministic variant on HIP. Measured on MI300X (ROCm 10.2): 2^22 float64 values over 16 orders of magnitude reduced into 64 keys, 11 runs: 3 to 5 distinct results with `ReduceByKey`, 1 with `deterministic_reduce_by_key`, at 2-4% more time for the whole scatter-sort-reduce. A test with a few thousand values runs in one block and cannot see the difference. (warp-1.15)

## Lesson for cuda-to-rocm: HIP_POINTER_ATTRIBUTE_MEMPOOL_HANDLE is not supported
Reference file: `references/platform-limits.md`. `hipPointerGetAttribute(..., HIP_POINTER_ATTRIBUTE_MEMPOOL_HANDLE, p)` returns `hipErrorNotSupported` (801) for a `hipMallocAsync` pointer and for a `hipMalloc` pointer alike (HIP 7.17, ROCm 10.2), and leaves that error as the last error. Code that classifies pointers as "pool" versus "plain device" memory through this attribute (as CUDA's `CU_POINTER_ATTRIBUTE_MEMPOOL_HANDLE` allows) sees every device pointer as plain device memory; track pool membership yourself where it matters, and clear the last error after the failed query. `HIP_POINTER_ATTRIBUTE_IS_MANAGED` and `MEMORY_TYPE` work (managed memory reports type 1, host, with IS_MANAGED 1). (warp-1.15)

## Lesson for cuda-to-rocm: printf and assert inlined at every call site can make a HIP debug compile 70x slower
Reference file: `references/performance.md` (or build-headers-macros.md). Symptom: a runtime-compiled (hipRTC) debug kernel that compiled in about 2 s takes minutes, and a debug test run looks hung (no GPU activity, one CPU core busy in the compile). Cause: a small bounds-check helper containing `printf` and `assert`, called from every indexing function and inlined everywhere; on AMDGPU `printf` lowers to a substantial hostcall sequence, so inlining it at every array access multiplies the code the optimizer sees. Measured on MI300X (ROCm 10.2), one tile reduction kernel at `-O3 -g -D_DEBUG`: 142 s, against 2.1 s with the helpers marked `__attribute__((noinline))` (the checks still run at every access). Fix: keep diagnostic helpers out of line on HIP. When timing compiles, disable ROCm's code object cache (`AMD_COMGR_CACHE=0`, cache in `~/.cache/comgr`), or a second run looks fast for the wrong reason. (warp-1.15)

## Lesson for moat-porting: stopping a `python -m warp.tests` run means stopping its process group
Reference: `## Fleet hosts`. The Warp test runner (and any `multiprocessing` pool runner) spawns worker processes that survive when only the parent is killed, or when the harness stops a backgrounded command at its time limit. The orphans kept a hung kernel running on the job's pinned GPU for over an hour, and every later run on that GPU (even a one-kernel smoke test) then stalled in module load, which first looked like a port regression. Start long runs with `setsid` and record the process group id; stop them with `kill -- -<pgid>`; afterwards confirm with `amd-smi process -g <gpu>` that no process of yours holds the GPU. (warp-1.15)

## Ruling on plan Q5, sort bit ranges ending at the key width (jeff, 2026-11-25)

(d): carry the rocPRIM fix in Warp's HIP build instead of changing Warp's sort algorithm. Root cause and tested fix are in ROCm/rocm-libraries#16299: `rocprim::detail::radix_merge_compare<Descending, true, T, identity_decomposer>` computes `radix_mask_upper = (T(1) << (current_radix_bits + start_bit)) - 1`, a full-width shift when the range ends at the key width. Preferred method: a small HIP-only Warp header with explicit specializations of that comparator (corrected constructor) for the key types Warp sorts, declared after the rocPRIM include and before first use, gated on a `ROCPRIM_VERSION` range (affected 4.4 through at least 5.1). Confirm which `T` the comparator is instantiated with for signed and `double` keys (rocPRIM's radix key codec). Fallback if a key type cannot be covered cleanly: `build_dll.py` writes a patched copy of the header into an include directory that comes first. Add tests of `[b, width)` ranges for every key type, keys and pairs, including the segmented sorts, at sizes in the merge-sort window (1025 to 2^20). Remove the 1.14 workaround in the vendored cuBQL `sah_builder.h` (full 64-bit sort under `__HIPCC__`) once the comparator fix is in.
