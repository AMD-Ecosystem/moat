# nvImageCodec notes

## Intake screen (2026-11-05, gap-matrix seed; matrix: partial, AMD alternative rocJPEG decode-only, rocDecode)

Recommendation: **decline**, SKIP_REASON `not-a-target` -- but this is not as clear as the other NVIDIA-library screens in this batch; see the question for jeff at the end.

- Licence: Apache-2.0 (tier 1, `utils/licenses.py check NVIDIA/nvImageCodec`). Per-file scan run because the take-up case is not empty: `git clone --depth 1 https://github.com/NVIDIA/nvImageCodec agent_space/nvImageCodec-screen` then `python3 utils/licenses.py scan-nvidia agent_space/nvImageCodec-screen` -> "no NVIDIA proprietary licence text". Submodules (pybind11, NVTX, googletest, dlpack, boost/preprocessor) are all permissive. Clean file by file.
- What it is: a codec framework (C API, codec registry, executor, Python bindings) that dispatches batched image decode/encode to per-format extensions. The GPU extensions (`extensions/nvjpeg`, `nvjpeg2k`, `nvtiff`) are thin wrappers over NVIDIA's closed nvJPEG, nvJPEG2000 and nvTIFF libraries; the CPU extensions (libjpeg-turbo, libtiff, OpenCV, nvbmp, nvpnm) are plain C++. Own CUDA source is tiny: 5 `.cu` files in a 985-path tree, one in the library (`src/imgproc/convert_kernel_gpu.cu`) and four tests.
- AMD equivalents: rocJPEG (`ROCm/rocm-systems/projects/rocjpeg`, AMD ROCm team) covers JPEG GPU decode, the main nvJPEG job, and AMD engineers are already integrating it into consumers directly (TorchCodec #1554/#1642, see the torchcodec screen); rocAL (`ROCm/rocAL`) is AMD's image decode/augment pipeline library (the DALI role). No AMD library exists for GPU JPEG2000 decode, GPU TIFF decode or GPU JPEG encode.
- Remaining gap: a HIP build of nvImageCodec would be the framework hipified (one conversion kernel) plus a NEW rocJPEG extension written from scratch; JPEG2000/TIFF/encode would stay on the existing CPU extensions, because there is no ROCm library to call. That is building an AMD backend for an NVIDIA product whose GPU value is the closed libraries, not porting CUDA code, and NVIDIA will not take it upstream.
- Downstream note: the main open-source consumers are rapidsai/cucim (`cucim.kit.cuslide2` loads nvImageCodec) and Project-MONAI/monai-deploy-app-sdk (`decoder_nvimgcodec.py`). AMD's hipCIM (`ROCm-LS/hipCIM`) carries `cucim.kit.cuslide` and `cucim.kit.cumed` but not `cuslide2`, so the AMD whole-slide path does not need nvImageCodec today; if it ever does, the ROCm-LS team owns that call.
- Duplicate check: upstream PR search for rocm/amd/hip returns nothing; no AMD fork found; README/docs carry no AMD mention.

Question for jeff: the gap matrix calls this "partial". Do you want a HIP build of nvImageCodec with a new rocJPEG decode extension (JPEG2000, TIFF and encode staying on its CPU extensions) as an AMD-Ecosystem fork-only deliverable, for consumers such as cuCIM cuslide2 / MONAI deploy that call nvImageCodec? The licence is clean file by file. Without that ask, I recommend the decline above.
