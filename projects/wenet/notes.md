### CUDA surface
- Only CUDA source: `runtime/gpu/tensorrt/LayerNormPlugin/LayerNormPlugin.cu` (4.5 KB), a TensorRT `nvinfer1` plugin for the TensorRT/Triton deployment path. TensorRT has no AMD equivalent API (MIGraphX is a different model), so this file is out of scope, not a port target.
- The training/inference package `wenet/` is plain PyTorch (`--device cuda` style; 12 `torch.cuda` sites). No compiled extension.

### GPU-specific dependencies and deployment paths
- k2 (MOAT project, ROCm support merged upstream via k2-fsa/k2#1353): OPTIONAL. Guarded imports in `wenet/models/k2/model.py` (LF-MMI / HLG decoding) and `wenet/models/transducer/transducer.py` (pruned RNNT loss, `enable_k2` default False; torchaudio RNNT loss is the default). Not a hard dependency, so no set-deps; a good place to exercise the k2 port.
- deepspeed is in requirements.txt (train engine option): upstream DeepSpeed supports ROCm; ROCm/DeepSpeed also exists.
- `runtime/gpu/` (Triton Inference Server): `tensorrt/`, `tensorrt_fastertransformer/` (NVIDIA-only), `cuda_decoders/` uses `riva-asrlib-decoder` (NVIDIA Riva CUDA WFST decoder, NVIDIA-only), and ONNX models via onnxruntime-gpu. `wenet/bin/export_onnx_gpu.py` / `recognize_onnx_gpu.py` need onnxruntime-gpu: ONNX Runtime has no ROCm EP any more, so none of these is an AMD path. Docs should say so.
- `runtime/libtorch` C++ runtime: `-DGPU=ON` downloads a CUDA libtorch and defines `USE_GPU`; a ROCm libtorch option is a possible small CMake + docs change (needs checking that the C++ code only uses `torch::kCUDA`, which maps to HIP in ROCm libtorch).

### Existing AMD effort
- No ROCm/HIP/AMD PR, branch or issue upstream (search hits #1305 "add GPU support to runtime/LibTorch", CUDA, and #2003, unrelated). Upstream has vendor runtimes for Kunlun, Horizon BPU, IPEX, OpenVINO, but none for AMD.
- No ROCm/ or AMD-Ecosystem repo. Web search: nothing for wenet on ROCm. amd / AMD-AGI orgs not searchable with this token (SAML SSO); that part of the duplicate check stays open.

## Lesson for cuda-to-rocm: protobuf built by g++ and used from clang code crashes in its parser (libraries.md or build-cmake-link.md)

Promoted to cuda-to-rocm/references/build-cmake-link.md in 9d8549ee.

**Build protobuf (and abseil) with the same compiler as the code that includes its generated headers.** Symptom: the first parse of a message segfaults inside `google::protobuf::internal::TcParser::FastMtS1` with a jump to a garbage address (`#0 0x... in ?? ()`); here MIGraphX's `migraphx-driver read model.onnx` crashed on any ONNX file. Cause: protobuf v30's table-driven parser calls its fast-path functions with a clang-only calling convention (`PROTOBUF_CC`); generated code and inline headers compiled by clang (the ROCm clang building a HIP project) call into a `libprotobuf.a` that g++ compiled with the default convention. Fix: build the dependency prefix with the ROCm clang (`cget init --cxx <rocm>/lib/llvm/bin/clang++`), then rebuild. Separately, when such a library is loaded into a process that already has another protobuf (onnxruntime), link it with `-Wl,--exclude-libs,ALL -Wl,-Bsymbolic` so it binds to its own copy. Seen building MIGraphX rocm-7.2.4 deps with cget on Ubuntu 24.04 (gcc 13, ROCm 7.12 clang), 2026-11. (wenet)

## Lesson for cuda-to-rocm: a C++ program linking TheRock's torch wheel LibTorch (build-cmake-link.md, LibTorch entries)

Promoted to cuda-to-rocm/references/build-cmake-link.md in 9d8549ee.

**TheRock's torch wheels cannot be linked from C++ as installed: their RUNPATH points into TheRock's CI tree.** Symptom: linking an executable against `torch/share/cmake/Torch` from a TheRock torch wheel warns `librocm-openblas.so.0, needed by libtorch_cpu.so, not found` and fails with undefined `sgemm_`/`zgetrf_` (and `librocm_sysdeps_liblzma.so.5` for aotriton); the same wheel works in Python. ## Lesson for cuda-to-rocm: an onnxruntime execution provider that fails at session creation falls back to the CPU silently (validation.md)

Promoted to cuda-to-rocm/references/validation.md in 9d8549ee.

**After creating an onnxruntime session for an AMD GPU, check `session.get_providers()`.** Symptom: a script that asks for `MIGraphXExecutionProvider` (or any GPU provider) runs, returns correct numbers, and is slow; stderr has an `EP Error ... Falling back to ['CPUExecutionProvider'] and retrying` block that is easy to miss in a long log. Cause: onnxruntime's Python API retries on the CPU provider when the requested provider fails to initialize (here an undefined symbol in a source-built `libmigraphx_gpu.so`). Fix: assert `get_providers()[0]` is the GPU provider in validation runs, and look for the provider's own compile log (`[MIGraphX EP] ... Model Compile: Begin`). ## Lesson for cuda-to-rocm: torch.cuda.device_count() returns 0 although HIP sees the GPU (diagnosis.md)

Promoted to cuda-to-rocm/references/diagnosis.md in 9d8549ee.

**A mismatched `amdsmi` Python binding makes `torch.cuda.device_count()` report 0 while `torch.cuda.is_available()` is True.** Symptom: `torch.cuda.is_available()` True, `torch._C._cuda_getDeviceCount()` 1, `torch.cuda.device_count()` 0, then `AssertionError: Invalid device id` on the first device query. ## Lesson for cuda-to-rocm: two ROCm versions in one process, a torch wheel's bundled HIP and a library built for a system ROCm (libraries.md or diagnosis.md)

Promoted to cuda-to-rocm/references/build-cmake-link.md in 9d8549ee.

**A PyTorch wheel that bundles its own ROCm runtime cannot share a process with a library linked against a different system ROCm.** Symptom: onnxruntime's MIGraphX provider (or any HIP library built for a system ROCm) fails to load after `import torch`, e.g. `libamdhip64.so.7: undefined symbol: hsa_amd_memory_get_preferred_copy_engine, version ROCR_1`, and onnxruntime quietly retries on `CPUExecutionProvider`. Cause: the download.pytorch.org ROCm wheels ship `libamdhip64.so`, `libhsa-runtime64.so` and friends in `torch/lib`; the bundled HSA runtime keeps the SONAME `libhsa-runtime64.so.1`, so when the other library's newer `libamdhip64.so.7` asks for `libhsa-runtime64.so.1`, the dynamic loader reuses the older copy torch already loaded. Fix: use a torch built for the same system ROCm that the other library targets (AMD publishes such wheels at `repo.radeon.com/rocm/manylinux/rocm-rel-<version>/`; they link the system ROCm instead of bundling it), and check `/proc/self/maps` for a single `libamdhip64`/`libhsa-runtime64` pair. Seen with torch 2.8.0+rocm6.4 and onnxruntime-migraphx 1.27.1 (built for ROCm 7.2.4), fixed with torch 2.8.0+rocm7.2.4 and ROCm 7.2.4, 2026-11. (wenet)

## Lesson for cuda-to-rocm: a local-package option must be a variable only the user sets, not `<Pkg>_DIR` (build-cmake-link.md)

Promoted to cuda-to-rocm/references/build-cmake-link.md in 9d8549ee.

**To let a CMake build that downloads a dependency use a local copy instead (a ROCm LibTorch in place of a downloaded CUDA one), add one explicit cache variable that only the user sets; do not infer the request from `<Pkg>_DIR`.** `find_package` writes `<Pkg>_DIR` into the cache itself, so after the first download configure the value is set although no user set it. `if(Torch_DIR)` then fires on every reconfigure and the download (with its CPU/GPU URL choice) never runs again. Each attempt to tell the user's value from the cached one misses a case: a string compare with the download directory fails under a symlinked checkout, because `find_package` caches the hint path as it was computed at the first configure, and a hint built with `get_filename_component(... REALPATH)` stays unresolved while the download directory does not exist yet (a build directory created after it existed caches the resolved path instead); a resolved compare plus an existence check fails for a relative value, which `if(EXISTS)` resolves from the current directory and `find_package` from the source directory. The fix is to stop inferring: declare e.g. `set(LIBTORCH_PATH "" CACHE PATH "...")`; when it is set, `find_package(Torch PATHS ${LIBTORCH_PATH} NO_DEFAULT_PATH)` and skip the download; when it is empty, leave the original code untouched. Declaring it as a PATH cache entry makes CMake turn an untyped relative `-D` value into an absolute path from the current directory. Three details: a set path with no package should stop configure with an error naming the variable, not fall back to the download (that silently builds against something else); do not load it `QUIET`, because a package whose config exists but rejects itself (libraries missing, wrong platform) explains why only in messages `QUIET` suppresses, and a config that reports through `find_package_handle_standard_args` leaves `<Pkg>_NOT_FOUND_MESSAGE` empty, so there is nothing to append to your own error; and a package config caches more than `<Pkg>_DIR` (LibTorch's caches `Caffe2_DIR` and the library paths it finds), so unset the entries that point into the package itself before loading the local copy, so it replaces a copy loaded earlier in the same build directory, and after, so that emptying the variable leaves no entry pointing into it. The entries the config's own dependency lookups cache (HIP, rocBLAS, ... for a ROCm LibTorch) stay, and the downloaded copy does not read them, so the result is not literally a fresh build directory; and if the local package's config stops configure with a fatal error, the cleanup after it never runs, and the download would then load the cached `<Pkg>_DIR` of the broken copy. CMake still writes the cache when configure stops on an error, so cover that case with an INTERNAL marker: `set(_LIBTORCH_PATH_LOADING ON CACHE INTERNAL "")` right before loading the local copy, `unset(_LIBTORCH_PATH_LOADING CACHE)` after the cleanup, and, before the branch that picks local or download, when the variable is empty and the marker is set, unset the package's entries and the marker. The download code stays untouched, and the marker is never set when the variable is not used (checked on CMake 3.14.4 and 3.31.6). Test with several configures in one build directory (download then local, local then download, CPU then GPU), from the checkout and through a symlink, with stand-in archives for the downloads. (wenet, 2026-11)

### The design (`runtime/core/cmake/libtorch.cmake`)

- The download branch is byte-for-byte be6ad97; the whole diff of that logic against upstream is `if(NOT IOS)` -> `elseif(NOT IOS)`. `Torch_DIR` is not read or tested anywhere by the new code; `runtime/libtorch/CMakeLists.txt` is back to upstream (zero diff).
- New cache entry, declared in `libtorch.cmake` just before its use: `set(LIBTORCH_PATH "" CACHE PATH "local LibTorch to use instead of downloading one")`. Name: it parallels `LIBTORCH_URL` in the same file (where the downloaded LibTorch comes from; this says where a local one is), and `*_PATH` is how the sibling `xpu.cmake` names user-given locations (`XPU_API_PATH`). The file has no `option()` lines of its own; the runtimes' options are single upper-case words (`GPU`, `TORCH`, `ONNX`), which a path variable cannot be. Maintainers may rename it.
- Set: `find_package(Torch QUIET PATHS ${LIBTORCH_PATH} NO_DEFAULT_PATH)`, no FetchContent. Accepts the LibTorch root, its `share/cmake/Torch`, or `share/cmake` (`torch.utils.cmake_prefix_path`); the README uses the wheel's `torch` directory.
- Set to a directory with no LibTorch (missing, or no `TorchConfig.cmake`): `FATAL_ERROR` "LIBTORCH_PATH is '<value>', which has no LibTorch (share/cmake/Torch/TorchConfig.cmake). Set it to a LibTorch directory, or unset it to download LibTorch." Chosen over a silent download, as instructed.
- Same-build-dir switching: `TorchConfig.cmake` caches `Torch_DIR`, `Caffe2_DIR`, `TORCH_LIBRARY`, `c10_LIBRARY`, `kineto_LIBRARY`, `C10_CUDA_LIBRARY` (the find calls in TorchConfig for a shared LibTorch on Linux, checked in the torch 2.8 wheel's config). With `LIBTORCH_PATH` set, these six entries are unset before `find_package` (so a LibTorch loaded earlier is replaced, not mixed: without it the simulation showed a stale `Caffe2_DIR` and `c10_LIBRARY` from the earlier LibTorch) and again after it (so emptying `LIBTORCH_PATH` reaches the untouched download code with nothing cached, exactly like a fresh build dir). [Corrected in Porter round 5 (review round 4 finding 2): no cache entry pointing into the local LibTorch remains, but the entries cached by its own dependency lookups (HIP, rocBLAS, MIOpen, ...) stay; the download does not read them. ## Lesson for cuda-to-rocm: TheRock's family torch device wheel carries no torch kernels (windows.md "A torch wheel needs the matching `[device-<gfx>]` extra", or linux-host-setup.md)

On Linux with ROCm 10.2 (`stable.repo.amd.com/rocm/whl-next`), torch is split into a host wheel plus device wheels at two levels: a family wheel (`amd-torch-device-gfx110x`, "AMD device kernels (RDNA3)") and a chip wheel (`amd-torch-device-gfx1100`). The family wheel holds only aotriton images (`torch/lib/aotriton.images/amd-gfx110x/`); torch's own kernels are in the chip wheel (`torch/.kpack/torch_gfx1100.kpack`). With only the family wheel, device detection is correct and the first kernel raises `torch.AcceleratorError: CUDA error: invalid kernel file` (`hipErrorInvalidKernelFile`, a different code from the `hipErrorInvalidImage` the existing entry names). Install the chip wheel (`amd-torch-device-<gfx>` or `torch[device-<gfx>]`); the family wheel alone is not enough. The existing entry sits in windows.md but the rule holds on Linux too. (gfx1100, torch 2.15.0+rocm10.2.0, 2026-11-25.)
