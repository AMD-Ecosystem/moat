### Licence

### CUDA surface
- Only CUDA source: `runtime/gpu/tensorrt/LayerNormPlugin/LayerNormPlugin.cu` (4.5 KB), a TensorRT `nvinfer1` plugin for the TensorRT/Triton deployment path. TensorRT has no AMD equivalent API (MIGraphX is a different model), so this file is out of scope, not a port target.
- The training/inference package `wenet/` is plain PyTorch (`--device cuda` style; 12 `torch.cuda` sites). No compiled extension.

### GPU-specific dependencies and deployment paths
- k2 (MOAT project, ROCm support merged upstream via k2-fsa/k2#1353): OPTIONAL. Guarded imports in `wenet/models/k2/model.py` (LF-MMI / HLG decoding) and `wenet/models/transducer/transducer.py` (pruned RNNT loss, `enable_k2` default False; torchaudio RNNT loss is the default). Not a hard dependency, so no set-deps; a good place to exercise the k2 port.
- deepspeed is in requirements.txt (train engine option): upstream DeepSpeed supports ROCm; ROCm/DeepSpeed also exists.
- `runtime/gpu/` (Triton Inference Server): `tensorrt/`, `tensorrt_fastertransformer/` (NVIDIA-only), `cuda_decoders/` uses `riva-asrlib-decoder` (NVIDIA Riva CUDA WFST decoder, NVIDIA-only), and ONNX models via onnxruntime-gpu. `wenet/bin/export_onnx_gpu.py` / `recognize_onnx_gpu.py` need onnxruntime-gpu: ONNX Runtime has no ROCm EP any more, so none of these is an AMD path. Docs should say so.
- `runtime/libtorch` C++ runtime: `-DGPU=ON` downloads a CUDA libtorch and defines `USE_GPU`; a ROCm libtorch option is a possible small CMake + docs change (needs checking that the C++ code only uses `torch::kCUDA`, which maps to HIP in ROCm libtorch).

### Existing AMD effort
- No ROCm/HIP/AMD PR, branch or issue upstream (search hits #1305 "add GPU support to runtime/LibTorch", CUDA, and #2003, unrelated). Upstream has vendor runtimes for Kunlun, Horizon BPU, IPEX, OpenVINO, but none for AMD.
- No ROCm/ or AMD-Ecosystem repo. Web search: nothing for wenet on ROCm. amd / AMD-AGI orgs not searchable with this token (SAML SSO); that part of the duplicate check stays open.

### torchaudio API check (plan rule R1)

**ROCm torchaudio has no GPU kernel for `rnnt_loss` or `forced_align`** in any build checked (TheRock 2.8 and 2.11 and download.pytorch.org 2.8.0+rocm6.4; `libtorchaudio.so` carries no HIP code). On a GPU tensor: `Could not run 'torchaudio::rnnt_loss' with arguments from the 'CUDA' backend ... only available for these backends: [CPU, Meta, ...]`. wenet's `force_align` moves its inputs to the CPU first (`wenet/utils/ctc_utils.py:116`), so alignment is unaffected; the transducer model's default loss (`transducer.py:180,495`, `enable_k2: false`) fails on the GPU. ## Lesson for cuda-to-rocm: protobuf built by g++ and used from clang code crashes in its parser (libraries.md or build-cmake-link.md)

**Build protobuf (and abseil) with the same compiler as the code that includes its generated headers.** Symptom: the first parse of a message segfaults inside `google::protobuf::internal::TcParser::FastMtS1` with a jump to a garbage address (`#0 0x... in ?? ()`); here MIGraphX's `migraphx-driver read model.onnx` crashed on any ONNX file. Cause: protobuf v30's table-driven parser calls its fast-path functions with a clang-only calling convention (`PROTOBUF_CC`); generated code and inline headers compiled by clang (the ROCm clang building a HIP project) call into a `libprotobuf.a` that g++ compiled with the default convention. Fix: build the dependency prefix with the ROCm clang (`cget init --cxx <rocm>/lib/llvm/bin/clang++`), then rebuild. Separately, when such a library is loaded into a process that already has another protobuf (onnxruntime), link it with `-Wl,--exclude-libs,ALL -Wl,-Bsymbolic` so it binds to its own copy. Seen building MIGraphX rocm-7.2.4 deps with cget on Ubuntu 24.04 (gcc 13, ROCm 7.12 clang), 2026-11. (wenet)

## Lesson for cuda-to-rocm: a C++ program linking TheRock's torch wheel LibTorch (build-cmake-link.md, LibTorch entries)

**TheRock's torch wheels cannot be linked from C++ as installed: their RUNPATH points into TheRock's CI tree.** Symptom: linking an executable against `torch/share/cmake/Torch` from a TheRock torch wheel warns `librocm-openblas.so.0, needed by libtorch_cpu.so, not found` and fails with undefined `sgemm_`/`zgetrf_` (and `librocm_sysdeps_liblzma.so.5` for aotriton); the same wheel works in Python. Cause: `libtorch_cpu.so`/`libtorch_hip.so` carry `RUNPATH $ORIGIN:/opt/python/cp311-cp311/lib/python3.11/site-packages/_rocm_sdk_devel/lib/host-math/lib:...`, valid only on the build machine; Python works because the `rocm_sdk` package preloads the SDK libraries. Fix for building and running: put the SDK's `_rocm_sdk_core/lib`, `lib/host-math/lib`, `lib/rocm_sysdeps/lib` and the `_rocm_sdk_libraries_<family>/lib` directory on `LD_LIBRARY_PATH` (GNU ld also searches it for indirect dependencies), or add them to the executable's RPATH with `--disable-new-dtags`. download.pytorch.org ROCm wheels bundle these libraries next to libtorch with an `$ORIGIN` RUNPATH. Seen with torch 2.8.0+rocm7.12.0 (gfx94X-dcgpu), 2026-11. (wenet)

## Lesson for cuda-to-rocm: torchaudio's ROCm builds have no GPU rnnt_loss or forced_align (libraries.md)

**torchaudio's RNN-T loss and CTC forced alignment run only on the CPU in ROCm builds.** Symptom: `NotImplementedError: Could not run 'torchaudio::rnnt_loss' with arguments from the 'CUDA' backend ... only available for these backends: [CPU, Meta, ...]` (same for `torchaudio::forced_align`) as soon as the inputs are on an AMD GPU. ## Lesson for cuda-to-rocm: an onnxruntime execution provider that fails at session creation falls back to the CPU silently (validation.md)

**After creating an onnxruntime session for an AMD GPU, check `session.get_providers()`.** Symptom: a script that asks for `MIGraphXExecutionProvider` (or any GPU provider) runs, returns correct numbers, and is slow; stderr has an `EP Error ... Falling back to ['CPUExecutionProvider'] and retrying` block that is easy to miss in a long log. Cause: onnxruntime's Python API retries on the CPU provider when the requested provider fails to initialize (here an undefined symbol in a source-built `libmigraphx_gpu.so`). Fix: assert `get_providers()[0]` is the GPU provider in validation runs, and look for the provider's own compile log (`[MIGraphX EP] ... Model Compile: Begin`). A MIGraphX built from an older tag than the SDK can also fail its run-time kernel compiles with `-Werror,-Wdeprecated-attributes` under a newer clang; MIGraphX appends `MIGRAPHX_GPU_HIP_FLAGS` to that compile (`-Wno-deprecated-attributes`). Seen with onnxruntime-migraphx 1.27.1, MIGraphX rocm-7.2.4, ROCm 7.12 SDK, 2026-11. (wenet)

## Lesson for cuda-to-rocm: torch.cuda.device_count() returns 0 although HIP sees the GPU (diagnosis.md)

**A mismatched `amdsmi` Python binding makes `torch.cuda.device_count()` report 0 while `torch.cuda.is_available()` is True.** Symptom: `torch.cuda.is_available()` True, `torch._C._cuda_getDeviceCount()` 1, `torch.cuda.device_count()` 0, then `AssertionError: Invalid device id` on the first device query. Cause: on ROCm, torch counts devices through `amdsmi` when it can import it, and that count wins over HIP's; an `amdsmi` binding from a different ROCm release than the one torch loaded returns no processor handles in torch's process. Fix: make the importable `amdsmi` the one from the same ROCm (TheRock: `_rocm_sdk_devel/share/amd_smi` of the matching SDK, e.g. via a `.pth` file), or remove the stray one from the path. Seen with a ROCm 10.1 `amdsmi` beside torch 2.8.0+rocm7.12.0, 2026-11. (wenet)
