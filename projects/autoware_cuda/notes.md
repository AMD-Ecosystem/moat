### What it is

A young repository (split out of autoware_universe per autowarefoundation/autoware#7340; last push 2026-11-10) holding Autoware's shared CUDA/TensorRT base packages. Three ament packages:

1. `autoware_cuda_dependency_meta`: CMake-only virtual package (no sources); its extras add `-fno-lto` to avoid duplicate `fatbinData` symbols. Trivial; the flag is harmless for HIP and may be needed for the same reason with HIP fat binaries.
2. `autoware_cuda_utils` (about 11 KB, header-only INTERFACE library): `cuda_check_error`, `cuda_unique_ptr`, `stream_unique_ptr`, `cuda_memory_pool`, `thrust_utils`, `cuda_gtest_utils`. CUDA runtime API (streams, `cudaMalloc`/`cudaHostAlloc`, `cudaPointerGetAttributes`, stream-ordered pool `cudaMemPoolCreate`/`cudaMallocFromPoolAsync`, `cudaSetDeviceFlags(cudaDeviceScheduleBlockingSync)`) plus Thrust (`device_vector`, `fill`, `count`, `thrust::cuda::par.on(stream)`). Links `CCCL::CCCL` through `cmake/find_cccl.cmake` (CUDA 13 CCCL layout).
3. `autoware_tensorrt_common` (about 3.3 KLOC host C++, no kernels): the `TrtCommon` engine wrapper every TensorRT node in autoware_universe uses. Requires TensorRT >= 10.

### CUDA surface and ROCm mapping

- `autoware_cuda_utils`: mechanical HIP port. All runtime symbols exist in HIP (`hipMemPoolCreate`, `hipMallocFromPoolAsync`, `hipPointerGetAttributes`, `hipSetDeviceFlags`); Thrust maps to rocThrust (`thrust::hip::par.on(stream)`), CCCL to rocThrust/hipCUB/libhipcxx. Known fault class to check: `hipPointerAttribute_t` field naming (`type`) and the managed/host memory-type values. Build: the test target uses legacy `find_package(CUDA)` + `cuda_add_executable` on `.cu` files and the library links `CUDA::cudart`; the port needs a HIP branch (`enable_language(HIP)`, `hip::host`, roc::rocthrust) and a replacement for `find_cccl.cmake`, keeping the CUDA path unchanged. Strategy A.
- `autoware_tensorrt_common`: no HIP analogue to translate into; this is a reimplementation with a defined target (MIGraphX), per Jeff's full-scope ruling. What a MIGraphX equivalent needs:
  - ONNX parse and compile: `nvonnxparser::createParser` + `IBuilder::buildSerializedNetwork` -> `migraphx::parse_onnx` + `program::compile(gpu target)`. Direct.
  - Engine cache: `.engine` serialization keyed by TensorRT version + JSON sidecar -> `migraphx::save`/`load` of the compiled program (`.mxr`), keyed by MIGraphX version and gfx target. Direct.
  - Precision: FP16 -> `quantize_fp16`; INT8 with `IInt8Calibrator` (implicit quantization, `tensorrt_conv_calib.hpp`) -> `quantize_int8` with calibration data; per-layer `setPrecision(kHALF)` on conv layers has no direct MIGraphX counterpart (it edits the network definition layer by layer). BF16/FP8 data types: partial.
  - Dynamic shapes: TensorRT optimization profiles (`kMIN/kOPT/kMAX` per input) -> MIGraphX dynamic dimensions (`onnx_options` dyn dims); semantics differ (MIGraphX compiles for ranges, with less mature dynamic-shape support), so the profile validation logic needs care.
  - Execution: `IExecutionContext::setTensorAddress` + `enqueueV3(cudaStream_t)` -> `program::run_async` with parameter maps on a `hipStream_t`. Direct in shape.
  - Plugins: `initLibNvInferPlugins` (standard TensorRT plugin library) has no MIGraphX equivalent; consumer models that rely on built-in TensorRT plugins need MIGraphX custom ops (`migraphx::experimental_custom_op`) or ONNX rewrites. The custom Autoware plugins live in autoware_universe (`autoware_tensorrt_plugins`, `autoware_tensorrt_bevformer`) and are that project's scope.
  - Profiling: `IProfiler` per-layer timing and `IEngineInspector` layer info -> MIGraphX `perf_report` / program print; approximate.
  - DLA (`setDLACore`, `DeviceType::kDLA`, `kGPU_FALLBACK`): Jetson-only, no AMD counterpart; stays CUDA-only.
  - API shape is the main design question: the public header exposes `nvinfer1::Dims`, `DataType`, `TensorIOMode`, `IBuilderConfig`, `INetworkDefinition` and `cudaStream_t`, and consumers in autoware_universe call these directly. Options for the planner: a parallel `autoware_migraphx_common` package with an equivalent API that consumers select at build time, or a backend-neutral layer under `TrtCommon` with TensorRT-free types. Either way the consumer side lands in autoware_universe, so the two projects' plans must agree on the interface.
- MIGraphX support is broadest on Instinct (gfx90a/gfx942/gfx950) and present but thinner on RDNA (gfx1100/gfx1201); the wave32 gate should be checked against MIGraphX's supported-target list before the planner commits to it.

### Risks

- The MIGraphX engine layer is new code, not a port, and the upstream (TIER IV maintainers) may prefer it as a separate package; whether it is offerable upstream as one PR is open.
- Dynamic-shape and INT8-calibration semantics differ from TensorRT; equal outputs on the dummy network do not prove the real perception models work.
- Validation needs ROS 2 (Humble/Jazzy) plus `autoware_cmake`, `autoware_lint_common`, `tensorrt_cmake_module` (the HIP path must not require it), and MIGraphX installed; fleet images carry none of ROS 2.
- `autoware_tensorrt_common` builds with `-Werror`; HIP/MIGraphX headers may trip warnings.

## Planning (2026-11-20, planner, linux-gfx950 fleet job; no GPU used, nothing built)

### Decisions for Jeff (rule before a porter starts)

Nobody could answer these during the planning job. plan.md is written for the recommended answer to each and says what changes otherwise.

**Q1. Shape of the MIGraphX engine layer (blocking; also fixes the interface autoware_universe builds against).** `TrtCommon`'s public API takes and returns TensorRT value types (`nvinfer1::Dims`, `DataType`, `TensorIOMode`, `cudaStream_t`), and autoware_universe's 16 consumer packages use them directly (240 uses of `nvinfer1::Dims`; the calibrators in yolox and classifier subclass `nvinfer1::IInt8*Calibrator`). Options:
- **A (recommended): same package, same classes, second backend.** On a ROCm build `autoware_tensorrt_common` compiles a new `src/migraphx_common.cpp` instead of `src/tensorrt_common.cpp` and installs HIP-only stand-in headers named `NvInfer.h` etc. that declare just the value types consumers use (written from scratch, not copied from NVIDIA). Consumers compile unchanged apart from `getNetwork()`/`getBuilderConfig()` users and direct TensorRT code. CUDA path: one `#if` around the class's private members and a code-motion split of the backend-neutral IO checks into `src/tensorrt_common_io.cpp`. Downside: a stand-in `nvinfer1` namespace in an Autoware package may not be welcome upstream.
- **B: new package `autoware_migraphx_common`** in this repository with Autoware-owned types and a mirrored API. CUDA package untouched; every autoware_universe consumer needs per-backend code (types and includes), a much larger diff there.
- **C: backend-neutral refactor:** replace the TensorRT types in `TrtCommon`'s public API with Autoware-owned ones on both backends. Cleanest design, but it changes the CUDA path's public API for every consumer and needs upstream's agreement before any code.

**Q2. INT8 on MIGraphX (blocking for the `int8` precision only).** TensorRT's path (`TrtConvCalib`: implicit-quantization calibrators, calibration-cache files, per-layer FP16 on conv layers, first/last-layer exclusion) has no one-to-one MIGraphX counterpart. Options:
- **a (recommended): implement int8 approximately.** Pull calibration batches from the caller's `IInt8Calibrator` (`getBatch`) into `migraphx::quantize_int8` calibration data, restrict quantized op types where possible with `add_op_name`, ignore per-layer/first/last-layer hints with a logged warning; TensorRT calibration caches are not reusable. Explicit Q/DQ ONNX models work natively. Real-model accuracy checks happen in autoware_universe (yolox, classifier).
- **b: no int8 on MIGraphX in this port.** `fp32`, `fp16` and `strongly-typed` only; `int8` fails with a clear error; int8 recorded as deferred work (`deferred.py add`).

**Q3. Delivery staging (blocking for scheduling).** autoware_universe's pure-CUDA stage (pointcloud preprocessor, ground segmentation, occupancy grid) depends only on `autoware_cuda_utils`, but the selector releases autoware_universe only once this whole project completes on a platform. Options:
- **i (recommended): two rounds, one PR.** Round 1 ports `autoware_cuda_dependency_meta` and `autoware_cuda_utils`, with every `autoware_tensorrt_common` item in surface.json moved to `owed` (accepted by the surface gate; `pr_ready` refuses while anything is owed, so no partial PR can open). Review and validate it, so autoware_universe's pure-CUDA stage unblocks. Round 2 adds the MIGraphX layer on the same branch (a new head, revalidation) before the single upstream PR. Round 2 has to be started deliberately (it will not be selected automatically once platforms show `completed`).
- **ii: one round.** Port both packages before review. Simpler bookkeeping; autoware_universe waits for the MIGraphX layer.
- **iii: two upstream PRs** (cuda_utils first, MIGraphX later). Partial-port PR; needs your explicit approval per the scope-cut rule.

**Q4. Proposed out of scope (confirm).** (a) TensorRT DLA (`dla_core_id`, `setDLACore`, `kGPU_FALLBACK`): Jetson hardware with no AMD counterpart; on MIGraphX a `dla_core_id != -1` request fails with an error. (b) TensorRT's built-in plugin library (`initLibNvInferPlugins`): no MIGraphX counterpart; models that need it are handled per model in autoware_universe (custom ops or ONNX rewrites). The `plugin_paths` dlopen mechanism itself stays, for MIGraphX custom-op libraries. These are listed as components in surface.json with "proposed out, pending Jeff (Q4)"; nothing is recorded as `scoped_out` until you rule.

## Lesson for cuda-to-rocm: protobuf built by gcc crashes a clang-built MIGraphX

For `linux-host-setup.md` (building ROCm libraries from source). Building MIGraphX from source with the ROCm clang against a protobuf (v30) built with the host gcc compiles and links cleanly, but every ONNX parse segfaults inside `google::protobuf::internal::TcParser::FastMtS1` (jump to a garbage address, called from `MessageLite::ParseFromIstream` in `libmigraphx_onnx`). Recent protobuf compiles its table-driven parser functions with a clang-only calling convention (`preserve_most`/`preserve_none` behind `PROTOBUF_CC`), so the clang-compiled generated code (`onnx.pb.cc`) and the gcc-compiled `libprotobuf` disagree on how those functions are called. Build protobuf with the same clang as MIGraphX (MIGraphX's own dependency script uses one compiler for everything). abseil is fine either way. (autoware_cuda)

## Lesson for cuda-to-rocm: MIGraphX names no outputs; take the IO table from the ONNX file

For `no-hip-equivalent.md` (TensorRT -> MIGraphX). TensorRT code addresses IO tensors by name and by index (inputs then outputs, in ONNX order). MIGraphX's API returns outputs by position only (compiled parameters `#output_0`, `#output_1`, ... with `offload_copy` off) and does not promise its parameter order, so the names and order have to come from the model: read `ModelProto.graph` inputs (minus initializers) and outputs, with their declared dims and elem types (a symbolic input dim is dynamic, -1); a ~300-line protobuf wire reader that seeks over the weights is enough, with no protobuf or ONNX dependency. Bind each output buffer as the `#output_N` parameter or MIGraphX allocates its own and the caller's buffer stays stale. Output dims the file leaves symbolic are not all dynamic: TensorRT reports -1 for a dimension that depends on a dynamic input dimension or on the values of tensors (data-dependent outputs such as NonZero or NMS; `NvInferRuntime.h`, `IExecutionContext::getTensorShape`), and the concrete value otherwise (exporters often leave `unk__N` or `<op>output_dim_0` on outputs of fully static models). With static inputs, resolve them from MIGraphX's own shape inference (the parsed program's output shapes), but note that for a data-dependent dim MIGraphX gives a static upper bound where TensorRT gives -1: a buffer sized from it holds the run, while a caller that expects -1 there sees a number (corrected per Review 2026-11-24e finding 6). With dynamic inputs, do not infer constancy by parsing at a few values with `onnx_options::set_default_dim_value`: a floor division (2x2 stride-2 pooling, a stride of 300 rows) gives equal lengths at small samples and differs later, so a dim reported as a number is then contradicted by real shapes; reporting -1 for every symbolic output dim is the safe choice, and consumers must give -1 for those dims. An output the file gives no shape still needs a rank (TensorRT always reports one): infer it from the ONNX operators where it follows from their definitions, and otherwise take it from a parse, checked against every compiled program, because MIGraphX's default length 1 can change the rank (`Squeeze` without axes drops the dim at 1, which TensorRT's parser refuses for a dynamic dim). MIGraphX represents a scalar as one element in one dimension (lens `{1}`, stride 0 in every parse probed here), and a one-element vector also has lens `{1}`, so a one-element output of a parse does not tell rank 0 from rank 1; a scalar is rank 0 to TensorRT. Also: MIGraphX's dynamic-shape mode compiles one submodule per value of a single dynamic dimension, so for wide TensorRT profiles compile per concrete shape (opt first, others on first use) instead. ## Lesson for cuda-to-rocm: MIGraphX ONNX parsing ignores registered custom ops; fp16 op lists and empty tensors

For `no-hip-equivalent.md` (TensorRT -> MIGraphX). (1) TensorRT plugin libraries supply ONNX operators by `op_type`; MIGraphX's `register_experimental_custom_op` registers an operation usable only in programs built through the API: `parse_onnx` still fails with "Unknown operator", and the parser's op-parser registry is not exported. Plan TensorRT-plugin models around that (graph partitioning, or an upstream parser change). (2) `quantize_fp16(program, quantize_op_names)` converts only the named instructions, and it does so after running `normalize_ops` and `optimize_module` on the program, which can replace operations (a division by a constant becomes `mul`); so "everything except X" needs the names of the operations present after those passes, not of the parsed model. The public API has no operation list (`get_operators()` lives in a private header) and the C++ `program` copy shares the underlying program, so parse the model a second time, run `quantize_fp16` on it with a list naming no real operation (the passes run, nothing is converted), and read the names from `program::print()`, which goes to `std::cout` and abbreviates any constant of more than ten elements to `{ ... }`. Do not save the program as JSON to get the names: that writes every weight as a list of integers (a 64 MiB model grew the process by about 2.7 GiB). An empty name list means every operation to MIGraphX. Whether an exclusion changes results depends on the graph, the fusions and the MIGraphX version: in one fused graph here (matmul, then sigmoid and softmax at the outputs) the activations came out in fp32 even under full fp16, so excluding them changed nothing measurable, while excluding the matmul did. (3) A zero-length input dimension is handled op by op, not by kind of op. Observed in MIGraphX f0239c965 at `[0, 4]` (`migraphx-driver read` and `compile --gpu` with `--input-dim @x 0 4`): a lone `Relu` compiles; `Add(x, x)` and `Transpose(x)` fail at compile, as does `Add(x, c)` with a constant `c [4]`, which parses to `multibroadcast` + `add` ("Global size must be greater than 0"); `ReduceSum` with `axes=[0]` parses to `{1, 4}` and fails at compile; `ReduceSum` with `axes=[1]` parses to `{0, 1}` and the compiler process dies with a floating point exception; the axis `broadcast` op that adds a convolution's bias fails at parse (`broadcast.hpp:135`, "output size (0) must be greater than or equal to s0 size"). When every output is empty the run can be skipped, which matches TensorRT. The `Relu` case works because of the ONNX parser, not the compiler (`parse_generic_op.cpp`, for the unary ops plus Concat, Gather, GatherND, Flatten, Identity and LRN): it drops the inputs that have no elements, and the op becomes an `undefined` instruction when every input is empty, or for Gather and GatherND when any operand is empty; none of this applies when any input shape is dynamic. `migraphx-driver read` already shows `undefined`, the compiled program has no `#output_N` parameter for that output, and its output shape reports 0 elements. So code that requires a parameter per output refuses exactly the programs that work, and a parse at the zero shape (when it succeeds) tells which outputs are empty. (4) MIGraphX's ONNX parser gives unbound symbolic dimensions the length 1; a model whose pooling window does not fit at 1 fails to parse unless a default dimension value is set. (autoware_cuda)

### Findings (open)

A. **A sampled "constant" output dim can be wrong, and the correction comes after the run that needed it: setup failure, or a device write past the consumer's buffer.** Code: `src/migraphx_common.cpp`, `resolveOutputDims` (about l.183-265), `forgetDimsThatDiffer` (about l.429-449), and the `enqueueV3` compile-then-run (about l.1130-1175).

- **Why:** a dim equal at the samples 2, 3, 64 and 255 is reported as known. `describeProgram` now checks programs only against the declared dims, so a program that contradicts the reported value is accepted and run in the same call. The reported value is changed only afterwards.
- **Reproduced by the reviewer** (child probe `agent_space/review-backend/probe_dims.cpp`, re-run on GPU 3) with `pool_network.onnx`, where `sparse` height = (H-1)/300+1, and profile min 2 / opt 250 / max 900:
  - NetworkIO `sparse` [1,2,-1,8], as TensorRT reports it: `setup()` returns false ("Invalid tensor ... Cached engine: sparse {[1, 2, 1, 8]}").
  - NetworkIO [1,2,1,8]: setup succeeds and `getTensorShape("sparse")` = [1,2,1,8]. A run at H=600 then returns true and overwrites 16 of 16 guard floats past a one-row buffer. Only after that does it report [1,2,-1,8].
- **The committed test passes only because** its opt (600) happens to expose the dim.
- **Comments overclaim:** the `kDimensionSamples` and `resolveOutputDims` comments ("corrected when a program is compiled") and the README line ("a program compiled later ... makes it -1") claim more than the code guarantees.
- **Fix options:**
  - (i) refuse a program whose output lens contradict a reported known dim, before binding, and reconsider the report;
  - (ii) report -1 for any dim the file leaves symbolic when any input is dynamic (TensorRT parity is lost only for dims that do not depend on the dynamic ones, the earlier finding-2 case);
  - (iii) resolve only by a proof stronger than sampling.

  Option (i) at least removes the out-of-bounds write.

B. **`Fp16ExclusionsDoNotSerializeTheWeights` is order-dependent and loose when run alone; it also needs `/proc/self/clear_refs` without saying so** (`test/migraphx_common_test.cpp`).

- **Reproduced:** run alone, `without` = 595 MiB (it includes about 310 MiB of one-time MIGraphX/HIP initialization) and `with` = 282 MiB. In the full suite the porter measured 287 and 282.
- **Consequence:** alone, the bound `without + 2 * weights` is about 720 MiB, so a regression of up to about 7x the weights passes. The comment "takes little more memory than building without" holds only for the full-suite order.
- **Fix:** do an unmeasured warm-up build first (or measure `without` again after `with` and take the smaller), and `GTEST_SKIP` with a reason when `clear_refs` cannot be written.

C. **`operationNames` swaps `std::cout`'s buffer process-wide** (`src/migraphx_common.cpp`, about l.315-330).

- **Why it is a defect:** the mutex serializes only this function. Another thread writing `std::cout` meanwhile races with `rdbuf()`, which is a data race on one stream object, i.e. undefined behaviour, not merely "lost output" as the comment says.
- **When it happens:** on every fp16 build with exclusions, including the per-shape compiles inside `enqueueV3()` while a node runs.
- **How verified:** read; MIGraphX `api.cpp:513` prints with `std::cout << p`, and the C API has no instruction iterator, so print is the only public route.
- **Fix:** keep the print route but run it where no other thread can be inside the process's `std::cout` use, for example once at `setup()` before inference starts, with per-shape compiles reusing that name set. The name set may be a superset: extra names select nothing. The comment must state the real constraint.

D. **Construction prints a MIGraphX error to stderr for models that need the fallback parse, and parses up to 9 times** (`initialize()`, about l.532-546).

- **Why:** the default-length attempt fails first, and the MIGraphX C API itself prints `migraphx_parse_onnx: Error: ... POOLING: not enough padding ...` on every construction, though a sample length then succeeds. Seen in the reviewer's probe output and the porter's test logs.
- **Cost:** a dynamic-input model is parsed up to 1+4 times for the check, plus 4 times in `resolveOutputDims`, each reading all the weights.
- **Fix:** reuse the successful sample parses between the two (parse once per sample length), and log that a first failure at length 1 is expected, or try the sample lengths first.

E. **Lesson item 3 overstates and names the wrong mechanism** (notes, "Lesson for cuda-to-rocm: MIGraphX ONNX parsing ignores registered custom ops; fp16 op lists and empty tensors").

### Findings

1. **Rank inference recurses once per node and crashes the constructor on a valid model** (`src/onnx_model_io.cpp` `RankInference::rank` -> `nodeRank` -> its `input` lambda -> `rank`). `nodeRank` reserves 2792 bytes of stack per level in the built library (child (a), objdump), so a graph output with no declared shape at the end of a chain of roughly 2500 to 4000 shapeless intermediates (8 MiB stack; fewer on a smaller thread stack) gets SIGSEGV inside `readOnnxModelIO()`, before MIGraphX parses anything: no exception, no log. Child (a): a TrtCommon probe at a072da8 constructs a 2500-node chain and dumps core at 3000, while the e850647 library constructs and sets up the 3000-node chain. Fix: walk the producers iteratively (topological order) or cap the depth and return nullopt; add the chain model to the tests.
2. **An inferred rank that MIGraphX's program contradicts now fails `setup()` for models that set up at e850647** (`src/migraphx_common.cpp` `outputDims`, inferred rank preferred with no cross-check, then `describeProgram`/`matchesDims`). For a shapeless `y = Unsqueeze(MatMul(a[4], b[4]), axes=[0, 1])` the inference says rank 2 (as ONNX and TensorRT do), but MIGraphX f0239c965 compiles `y` as `{1}`, so `setup()` fails with `Compiled program has shape [1] for output y, which does not match its dimensions [-1, -1]` (child (a) probe: setup 0 at a072da8, 1 at e850647). Fail-safe (nothing overruns), but a regression; the root cause is MIGraphX's unsqueeze of a scalar, an upstream defect worth a report. The same class: Squeeze with an empty axes tensor (ONNX keeps every dim, MIGraphX drops the 1-length ones). Fix: decide what is reported when the ranks disagree only by length-1 dims (equal element count), or refuse with a message naming the MIGraphX disagreement rather than the generic shape mismatch; add a test either way.
3. **The second parse can reuse a length already known to fail** (`src/migraphx_common.cpp:606-608`). When the construction parse succeeded only at 256 (1 and 64 failed), `parsed_length == 64` is false and the second parse uses 64 again, which throws; the rank stays unknown and the constructor refuses with `Cannot tell the rank of output ...`. Read from the code (attempt order 1, 64, 256); no model built. Fix: choose a length not already tried and failed.
4. **Test claims stronger than the tests** (`test/migraphx_common_test.cpp`):
   - `OutputRanksFollowTheModelsOperators` (l.1356-1358, "covering each way the rank is inferred from the model") and the generator docstring (`generate_conv_network.py:12-13`): x is static, so a missing rule falls back to MIGraphX's rank, which is right for every non-scalar output. Against e850647 (no inference at all) the test fails on only 3 of 28 outputs (total, size, nonzero). The rules matter for telling rank 0 from a one-element rank 1, which only `total` and `size` exercise. Add scalar and [1] outputs per rule (Squeeze, Gather with a scalar index on a vector, MatMul 1x1, Reduce over all axes, ArgMax of a vector, Constant) or reword the comment.
   - `OneElementOutputIsNotTakenForAScalar` (l.1316-1320) says "Its rank follows from the model, so y is reported as [-1]"; the second parse gives the same result without the ReduceSum rule (the test also passes on e850647). Reword, or add a static one-row variant, where only the inference can answer.
   - `OutputThatMayBeAScalarIsRefusedWhenItsRankIsNotKnown` (l.1345-1348) accepts any constructor exception; the refusal path is shown only by the log. Assert the cause (capture the log) or note it.
   - Pre-existing (generator l.262): "its ReLU, the same flattened to [rows * 4]": `shapeless_output_flat.onnx` is `Reshape(x)`, not a flattened ReLU. That is also why the new rebuilt-program run in the cached-rank test is discriminating (a stale flat program returns raw x, negatives included).
5. **Commit and record text** (a072da8 body, unchangeable; the record and any PR body must not repeat it): "so no output is ever reported with a rank it may not have" is false for `squeezed.onnx` (reported [-1] before `setup()`, rank 2 at any row count but 1; the passing `OutputRankThatDependsOnTheInputShapesIsRefused` asserts exactly that); "parsed again at other lengths" is one parse at one length, and it runs also for an output whose parsed shape is dynamic, not only a one-element one; "Against the previous library, the scalar output, scalar input and unknown-rank tests fail" omits `OutputRanksFollowTheModelsOperators`, which also fails there (total, size, nonzero); the Test Plan's `a & b; wait` returns 0 whatever the background run's status. In the fifth pass, the e850647 logs cited (`mgx-test-oldlib*.log`) were taken with an earlier revision of the test file (failure lines :1287/:1341/:1265 vs :1292/:1346/:1266 at a072da8, and before the rank test existed); child (b) re-ran the a072da8 test file against e850647 and the described failures carry over, plus the OutputRanks one.
6. **Lesson "MIGraphX names no outputs" and the fifth pass's "For Jeff" premise are wrong about MIGraphX** (notes l.502 and the fifth-pass bullets on the design point): MIGraphX f0239c965 gives a data-dependent dim a *dynamic* shape, not a static upper bound (`NonZero` on static x [2, 4]: `dyn_slice ... {2, main_NonZero_1[0..8]}`; NMS: `{main_NonMaxSuppression_3[0..10], 3}`; `output_ranks.onnx` `nonzero`: `{3, main_NonZero_53[0..24]}`). `parsedOutputLens` maps a dynamic shape to nullopt, so such a dim stays -1, as with TensorRT; the design question as posed for Jeff does not arise for these operators (whether such a program then compiles and binds was not probed). The lesson also cites `IExecutionContext::getTensorShape` for "-1 for a dimension that depends on a dynamic input dimension"; on a context such a dim is -1 only until `setInputShape()` is called (`NvInferRuntime.h:4432-4436`); the call that keeps -1 is `ICudaEngine::getTensorShape` (l.3171-3176). Reword both before promotion.
