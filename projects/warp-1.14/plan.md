- Name: `warp-1.14` (release line of NVIDIA Warp 1.14)
- Upstream: https://github.com/NVIDIA/warp, branch `release-1.14` at `3601b2d07708` (one commit past tag `v1.14.0`)
- Fork: https://github.com/AMD-Ecosystem/warp. Pristine mirror `release-1.14` (review base, written only by `mirror-branch`); port branch `release/1.14.0.amd0`; both start at `3601b2d07708`.

- Binding rulings (Jeff Daily, 2026-11-10 / 11-11 / 11-18; `git show origin/port/warp:projects/warp/notes.md`): port independently from pristine `release-1.14`; AMD's 1.13 subset and `amd-integration-halo` are reference only (credit authors for any hunk taken); full HIP on wave64, wave32 and Windows gfx1151; release wheels `1.14.0+rocm.0` on Linux and Windows are part of the port; NVIDIA-only GPU libraries get ROCm equivalents; the documented build command must just work; no silent scope cuts.

## Existing AMD support

Classification: **improvable, authoritative but not reusable as a base.**

- `AMD-Ecosystem/warp` (formerly ROCm/warp) is AMD's own HIP port, maintained by AMD engineers: `release/1.13.0.amd0` (shipped with ROCm 26.10), `amd-integration` (tip `36ed75aa`, 2026-11-02), `amd-integration-halo` (gfx1151, tip `74014999`, 2026-08-21). Authoritative.
- It is reference material only, by ruling (2026-11-11), because the 1.13 delta is wave64-only (`WP_TILE_WARP_SIZE 64` for every HIP target), breaks every Windows build (`build_dll.py:143` NameError), regresses the CUDA path (HIP auto-replaces CUDA, `wp_cuda_device_get_arch` ABI change, lost CUDA < 12.3 capture guard), stubs device texture sampling to 0, and hides gaps behind about 35 weakened test files. Full review: plan file `warp-113-amd-delta-review.md` and the development-line notes.
- Reusable subset, used as reference and credited where a hunk is taken: `527ba15c` "HIP initial port" (deepsek, +2668/-364, 62 files), `da56e495` "test: fix unittests" (deepsek, +859/-386, 55 files), `7b941c21` (deepsek, +4), `51b16761` "HIP build fixes for upstream v1.13 additions" (rtmadduri, +118/-7), and only the tile_stack destructor hunk of `5b3130e9` (rtmadduri). Command: `git log -1 --format=... <sha>; git show --shortstat --format= <sha>`.
- `amd-integration-halo` is the better reference for three specific problems this plan must solve: the wave32/wave64 lane mask (`tile.h:200-215` keyed on `__GFX9__`, 64-bit `tile_mask_t` on every HIP target), the bf16 atomic, and device texture sampling. It is Linux-only and auto-enables HIP.
- Delivery-vehicle note: upstream NVIDIA does not take AMD support (closed HIP shim PRs #1770, #1932) and does not link platform forks; the release line itself is the vehicle, so no upstream PR is planned or possible.
- Port vs rewrite: the performance-critical kernels that NVIDIA tunes with vendor libraries are the libmathdx paths (cuBLASDx/cuSolverDx/cuFFTDx, LTO-linked device functions). There is nothing to translate them into mechanically. This line is **correctness-first**: it uses the in-tree cooperative scalar GPU paths upstream already ships for builds without libmathdx (see "libmathdx" below). An AMD-native fast path (rocWMMA/MFMA/WMMA for `tile_matmul`) is a later pass, and only after open question Q1 is answered; AMD's 1.13 rocWMMA path is not carried (it breaks 16x16 fp32 `tile_matmul` at the default `block_dim=256` and has no RDNA fragment).

## Build classification

**Neither CMake nor a torch extension.** `ext_type`: `python-build-nvrtc` (custom Python build driver + runtime-compiled kernels + dynamically loaded driver API; the third class in `cuda-to-rocm`).

Evidence:
- `build_lib.py:225-640` is the documented build entry (`docs/user_guide/installation.rst:148-177`, `compatibility.rst:111-118`: `python build_lib.py`). It drives `warp/_src/build_dll.py`, which invokes the compilers directly: nvcc for `.cu` (`build_dll.py:670-672` Windows, `:794-796` Unix), `clang++ --cuda-gpu-arch` for the experimental `--clang-build-toolchain` (`:800-802`), MSVC `cl.exe` (`:610`) or `$CXX` (`:744`) for host `.cpp`. No CMake, no setuptools extension, no torch.
- The AOT library `warp.so`/`warp.dll` compiles 11 `.cu` files (`build_lib.py:521-533`) and 19 `.cpp` files (`:493-514`).
- Kernels users write are generated C++ compiled at run time by NVRTC: `wp_cuda_compile_program` (`warp/native/warp.cu:4395-4735`), options built at `:4460-4560`, output PTX/CUBIN/LTO-IR, loaded through `cuModuleLoadDataEx_f` (`:5066`). CPU kernels go through `warp-clang` (bundled LLVM, `warp/native/clang/clang.cpp`).
- The driver API is loaded at run time, not linked: `LoadLibraryA("nvcuda.dll")` / `dlopen("libcuda.so")` (`warp/native/cuda_util.cpp:174-187`), then `cuGetProcAddress` for 75 entry points (`grep -o "pfn_cu[A-Za-z0-9]*\b" warp/native/cuda_util.cpp | sort -u | wc -l` = 75).
- Packaging: `setup.py` (prebuilt binaries copied from `warp/bin`, `bdist_wheel` platform tag override, `license_files=["LICENSE.md", "licenses/*.txt"]`), `pyproject.toml:31,80-81` (`version` from `VERSION.md`).
- C++ examples under `warp/examples/cpp/` are separate CMake projects (`project(... CUDA CXX)`, `find_package(CUDAToolkit)`), each with a CTest test.

## Port strategy

**A compat header plus a HIP backend in the Python build driver and in the runtime compiler, with per-site guards only where semantics differ.** Strategy-A-shaped, written by hand because the build is not CMake.

1. One compat header `warp/native/hip_compat.h` (name final at porter's discretion; AMD's 1.13 calls it `hip_util.h`, 578 lines), included from `cuda_util.h` and from the `.cu` files only when the build defines `WP_ENABLE_HIP=1`. It maps the CUDA runtime (95 distinct `cuda*` identifiers: `grep -ohE "\bcuda[A-Z][A-Za-z0-9_]*" warp/native/*.cu warp/native/*.cpp warp/native/*.h | sort -u | wc -l`), the driver API (75 `pfn_cu*`), and NVRTC to HIP/hipRTC, and maps `cub::` to `hipcub::`. On CUDA builds it is never included, so the CUDA build is byte-identical.
2. `build_dll.py`/`build_lib.py` gain an explicit HIP backend: `--rocm-path`/`--hip` and `--hip-arch` options, `hipcc`/ROCm clang for `.cu`, `--offload-arch` list, `-DWP_ENABLE_HIP=1`, linking `amdhip64` + `hiprtc`, libmathdx forced off. **HIP is never auto-selected over CUDA**; it is selected by an explicit option (or by `--no-cuda`-style mutual exclusion that errors when both are requested). A host with only ROCm and no CUDA Toolkit gets a clear message pointing at the option, not a silent CPU-only build. Exact UX is open question Q6.
3. `wp_cuda_compile_program` gets a hipRTC branch (code object output, gfx target string, hipRTC option spelling, no PCH, no LTO).
4. Per-site guards for semantic differences only: the device-compile predicate (`__CUDA_ARCH__` sites), inline PTX `asm` blocks (HIP branch first), wavefront width in the tile collectives, conditional graph nodes, CUDA-version gates, and texture sampling.

Why this beats the alternatives:
- **hipify (source rewrite)**: would rewrite 95 runtime + 75 driver identifiers across `warp.cu` (5409 lines), `cuda_util.cpp` (1030), `cuda_util.h` (387) and 10 other `.cu` files, and every later line (`warp-1.15` .. `warp-1.19`, plus the development line) would have to re-hipify and re-resolve conflicts in the same files on each upstream merge. A header keeps the diff in those files to the genuine HIP branches. `wc -l` from `wc -l build_lib.py warp/_src/*.py warp/native/...` above.
- **Per-site guards everywhere** (`#ifdef __HIP_PLATFORM_AMD__` at each call): hundreds of sites, unreadable, and the same carry-forward cost.
- **torch hipify (Strategy B)**: not applicable; Warp is not a torch extension.
- **Defining `__CUDA_ARCH__` globally in the AOT hipcc build**: would leak into hipCUB/rocPRIM/rocThrust device passes and flip Warp's numeric `__CUDA_ARCH__ >= N` gates into PTX `asm` (fault class "a compat header that defines `__CUDA_ARCH__`"). Rejected for the AOT build. The runtime compiler is handled separately (below), because the ruling requires it to serve `__CUDA_ARCH__`-gated user code.

### Device-compile predicate and the runtime compiler (ruling 2)

Measured on AMD Warp `ac540f59` (IsaacLab notes, 2026-11-10): under hipRTC `defined(__CUDA_ARCH__)` is false and `__HIP_DEVICE_COMPILE__` is true, so `__CUDA_ARCH__`-gated code takes the host branch. Newton VBD's `wp.func_native` snippet (`#if defined(__CUDA_ARCH__) nextafterf(...) #else __builtin_nextafterf(...)`) then fails to link, and `texture.h` `sample_2d` (`texture.h:817` in AMD's tree) calls a host function from device code. Warp 1.14 has 109 `__CUDA_ARCH__` occurrences in 16 headers (`grep -o "__CUDA_ARCH__" warp/native/*.h warp/native/*.cu warp/native/*.cpp | wc -l`; per file: builtin.h 42, tile.h 17, texture.h 9, tile_solve.h 6, tile_reduce.h 5, tile_bvh/tile_cholesky/tile_matmul/tile_mesh 4 each, crt.h 3, bvh.h/tile_radix_sort.h/tile_scan.h 2 each, intersect.h/svd.h/tile_fft.h 1 each), of which 9 are numeric (`builtin.h:357,452,471,2091,2125,2129,2170,2262,2362`) and all select inline PTX or SM-feature paths. Plus 33 in `nanovdb/` and 38 in `cuBQL/` (`grep -roE "__CUDA_ARCH__|__CUDACC__|__CUDACC_RTC__" <dir> | wc -l`).

Plan:
- **Warp's own headers** become compiler-independent: every boolean `defined(__CUDA_ARCH__)` gate becomes `defined(__CUDA_ARCH__) || defined(__HIP_DEVICE_COMPILE__)` (mechanical; AMD's 1.13 does the same, reference `527ba15c`), and every numeric gate gets a HIP branch **before** it (`#if defined(__HIP_DEVICE_COMPILE__) ... #elif __CUDA_ARCH__ >= 800`). This makes the headers correct under hipcc (AOT) and hipRTC alike, whatever `__CUDA_ARCH__` holds.
- **hipRTC kernel compiles additionally define `__CUDA_ARCH__`** (in the hipRTC option list in `wp_cuda_compile_program`, HIP branch only), so user `wp.func_native` snippets and downstream projects (Newton, mujoco_warp, Kamino's `_sync_threads`) that gate device code on `__CUDA_ARCH__` take their device branch. Because Warp's own numeric gates are HIP-first, the value only affects user code. The value is open question Q2.
- `__CUDACC_RTC__` (11 occurrences, `grep -o`): hipRTC defines `__HIPCC_RTC__`; the `tile.h:17-67` and `builtin.h:2097,2162` gates and the `volume.h:15-23` PNanoVDB trick each get the HIP spelling. Whether HIP clang defines `__CUDA__` (used in `tile.h:17,20,41,67` as `defined(__clang__) && defined(__CUDA__)`) must be checked by the porter with a one-line probe, not assumed.
- `cuda_crt.h` (1446 lines, 714 `__nv_*` libdevice references, 16 inline `asm` blocks, warp intrinsics at `:459,1347-1414` with 32-bit masks and `width = 32`) is the NVRTC/Clang-CUDA libc replacement. Under hipRTC the HIP builtin headers provide math, half, and intrinsics; `crt.h:237` must not include `cuda_crt.h` under hipRTC, and anything Warp's generated code needs from it (e.g. `nextafter`, `__half` helpers) maps to `__ocml_*` / HIP's own. `warp/native/libdevice/libdevice.10.bc` is NVIDIA-only and stays out of the HIP path.

### libmathdx (ruling 4)

What the features need, from source:
- Build: `build_lib.py:309-313` `--use-libmathdx` defaults on and downloads NVIDIA libmathdx 0.3.x (`deps/libmathdx-deps.packman.xml`, `developer.nvidia.com/downloads/compute/cublasdx/...`); `build_dll.py:581-586,687-692,817-821` adds `-DWP_ENABLE_MATHDX=1`, links `mathdx`/`mathdx_static` and `nvJitLink`. At run time `warp.cu:4373-5002` generates LTO-IR through `cublasdx*`/`cusolverdx*`/`cufftdx*` (77 references, `grep -cE "cublas|cusolver|cufft" warp/native/warp.cu`) and links it with nvJitLink.
- Every libmathdx feature has an in-tree **GPU** path when `WP_ENABLE_MATHDX == 0`, which upstream ships and tests: `tile_matmul.h:370,420,480,561` (cooperative scalar GEMM; the header says it is not solely a fallback and wins for small tiles, `:4-14`), `tile_cholesky.h:276,326,413` (cooperative scalar Cholesky and adjoint), `tile_solve.h` (6 gates), `tile_fft.h:316` (cooperative radix-2 on shared memory). Python dispatch already routes there when `wp_is_mathdx_enabled()` is false (`builtins.py:13090,13320,13581,13863,14078,14278`). Upstream has dedicated tests: `tile/test_tile_matmul_no_mathdx.py`, `test_tile_cholesky_no_mathdx.py`, `test_tile_solve_no_mathdx.py`, `test_tile_fft_no_mathdx.py`.
- ROCm has no device-callable, LTO-linkable equivalent of the Dx libraries: rocBLAS/hipBLASLt/rocSOLVER/rocFFT/hipFFT are host-launched; rocWMMA is a device-side matrix-fragment API (GEMM only) and Composable Kernel is a template library, neither a drop-in for cuSolverDx or cuFFTDx.
- Therefore the HIP build sets `WP_ENABLE_MATHDX=0`, never fetches libmathdx, never links nvJitLink, and uses the upstream cooperative GPU paths: these are GPU implementations, not CPU fallbacks. One concrete capability gap results: **`tile_fft` on GPU without libmathdx supports only power-of-two sizes divisible by `block_dim`** (`builtins.py:13435-13448`; non-power-of-two raises `ValueError`). That gap, and whether a rocWMMA `tile_matmul` fast path belongs in this line, are open questions Q1 and Q3.
- The `+rocm` wheel contains no libmathdx, no nvJitLink, no NVRTC, no cudart: the HIP build links none of them, and the packaging step drops `licenses/cuda-LICENSE.txt` and `licenses/libmathdx-LICENSE.txt` from `license_files` for the ROCm wheel (keeping `nanovdb-LICENSE.txt` and Warp's own; adding a ROCm notice only if a ROCm component is redistributed, which this plan does not do).

### Version string

`1.14.0+rocm.0` must appear identically in `VERSION.md` (wheel metadata, `pyproject.toml:80-81`), `warp/config.py:122` (`config.version`), and `warp/native/version.h:7` (`WP_VERSION_STRING`, regenerated by `build_lib.py`'s `generate_version_header` from `config.version`). `wp_init` rejects a native/Python mismatch (`context.py:5983`, `test_version.py:26-30` exact match; the regex `^\d+\.\d+\.\d+` still matches). The kernel cache directory is keyed on `config.version` (`build.py:168-174`), so `+rocm.0` also keeps HIP kernel caches apart from a CUDA install of 1.14.0. These three edits are one small commit on the port branch. `handle_ci_nightly_build` is GitLab-only and untouched.

## Risk list

1. **Wavefront width in every warp-size-dependent kernel.** `WP_TILE_WARP_SIZE 32` (`tile_reduce.h:14`) and 32-bit lane masks are hard-coded. Sites that must change on HIP: `tile_reduce.h:57-160` (`__shfl_down_sync(mask, ..., WP_TILE_WARP_SIZE)`, `mask == 0xFFFFFFFF` full-warp test at `:94,122`, `1 << ((threadIdx.x + offset) % WP_TILE_WARP_SIZE)` at `:103,135` which is undefined for a 64-bit lane index: needs `1ull`), `:160,220,317,371,442,690` (`__ballot_sync(0xFFFFFFFF, ...)` then `__ffs(mask)`: needs a 64-bit mask type and `__ffsll`), `tile_scan.h:61,80` (`__shfl_up_sync(0xffffffffu, value, i, 32)`: width hard-coded 32 while `:137-139` index warps by `WP_TILE_WARP_SIZE`, so a 64-wide build would scan two 32-lane halves and combine them as one warp), `tile_scan.h:93` (`sums[1024 / WP_TILE_WARP_SIZE]`: scales as blockDim/warpSize, so 32 is the safe lower bound: keep it sized for 32), `tile_radix_sort.h:154-155` (`__shfl_xor_sync(0xFFFFFFFFu, ...)`), `:181-196` (`__syncwarp()`), `:460-473`, `:496-497` (`thread_id / 32`, `thread_id & 31`), `:531,612,632-633`, `:759,794`. Design: on HIP, `WP_TILE_WARP_SIZE` comes from the device: the host passes `--define-macro=WP_TILE_WARP_SIZE=<hipDeviceProp_t::warpSize>` to hipRTC (exact per device, also correct for an RDNA part run in wave64 mode), and the AOT hipcc build derives it from `__GFX9__` (gfx9 = 64, gfx10+ = 32, AMD halo branch precedent); a lane-mask type `tile_mask_t` (64-bit on HIP) with `tile_full_mask` derived from `WP_TILE_WARP_SIZE`; every literal 32/31/`0xFFFFFFFF` in the three headers replaced by those. The CUDA expansion stays textually identical. Also: a launch whose block is narrower than one wavefront (`block_dim` 32 on wave64) makes `blockDim/warpSize` 0: tests with `block_dim < 64` must run on wave64 and the warp-count math must round up (it does at `tile_reduce.h:199`; check every site). Shared-code rule: every change must be correct for 32 and 64.
2. **hipRTC differs from NVRTC.** No PTX (code object only) and no `nvrtcGetSupportedArchs`; no precompiled headers (`-pch`, `context.py:3102` `pch_dir`), no `--device-as-default-execution-space` (functions in user snippets without `__device__` are host-only under clang: Warp's `CUDA_CALLABLE` covers its own code, user `func_native` snippets must be probed), no `--extra-device-vectorization`/`--restrict`/`--diag-suppress`/`--Ofast-compile`; `--fmad=false/true` maps to `-ffp-contract=off/fast` (clang contracts across expressions, nvcc within: fault class; prefer `-ffp-contract=on` for the `fuse_fp` default if tests show drift); `--use_fast_math` maps to `-ffast-math` (watch NaN/inf semantics in `test_fast_math.py`); `-G` device debug unsupported; `--generate-line-info` maps to `-gline-tables-only`. hipRTC needs its builtin headers (`libhiprtc-builtins`) and, under TheRock layouts, `ROCM_PATH`-relative include dirs (`float.h`): Warp must locate them itself, not via README environment variables (ruling 5). AMD's 1.13 tree carries an `optnone` workaround on tile `atomic_add` for a hipRTC -O3 miscompile and a "HIPRTC can crash" test change: both must be re-derived against the current ROCm, with a reproducer and a deferred registration if real.
3. **Device-compile predicate**: above. Missing one gate silently compiles the host branch into device code (texture `sample_2d` precedent).
4. **Rule-of-five on texture/array/surface handles** and graph/user-object handles: HIP faults on double destroy where CUDA tolerates it (`texture.cpp:180,364`).
5. **256-byte texture pitch** for pitched 2D binds; layered arrays collapse across launches on gfx90a; use non-layered 3D arrays.
6. **OOB neighbour reads and zero-init**: audit `bvh.cu`, `mesh.cu`, `hashgrid.cu`, `sparse.cu`, `volume_builder.cu` for read-modify-write on fresh allocations without a memset (ROCm does not hand back zeroed pages) and one-past-end reads.
7. **Library swaps**: CUB -> hipCUB (temp storage >= 4 bytes; segmented ops on all-NaN input); hipCUB radix sort inside graph capture.
8. **Floating point**: `__fsqrt_rn` 1 ULP high on gfx90a; FMA contraction; host `min`/`max` overloads in `.cu` host code exist only for `int` under HIP (float args truncate): grep `bvh.cu`/`mesh.cu` host helpers; negative float to `uint64_t` cast. Tolerances are re-derived per test, never loosened for CUDA; loosening on HIP needs a measured cause.
9. **Atomics**: `atomic_cas` spinlock test (AMD 1.13 replaced it with a lock-free counter citing no independent forward progress): measure; a 20-CU gfx1151 APU starves cross-wavefront spin loops under contention (stdgpu precedent), so a hang there is a known fault class, not proof the port is wrong.
10. **Conditional graph nodes** absent on HIP (Q4); event timing inside graphs and external events in graphs are ROCm-limited (AMD 1.13 skipped `test_streams.py:337,366`): re-measure each.
11. **Multi-GPU graph mempools**: AMD 1.13 restricted capture tests to ordinal 0 (`test_fem_integrate.py:583`, `test_sparse.py:1099`), hiding a real fault on non-primary devices. Reproduce on a multi-GPU wave64 host; fix or register it.
12. **Windows (clang-cl)**: ROCm on Windows means clang-cl for every host TU that includes HIP headers (`cuda_util.cpp`, `warp.cpp`, the `.cpp` files that include `cuda_util.h`) and ROCm clang for `.cu`; `build_dll.py`'s MSVC branch (`:600-700`) passes `/MT` and MSVC-only flags that clang-cl mostly accepts, but HIP's `-fgpu-rdc` must be avoided (TheRock Windows bundler fault) and is not needed (no cross-TU device calls in Warp's AOT `.cu`). warp-clang (CPU JIT, bundled LLVM) stays on MSVC because it includes no HIP header. Runtime DLL resolution: `amdhip64_7.dll` and `hiprtc*.dll` must come from the ROCm SDK the build used, not a stale driver copy in System32 (observed on the gfx1151 laptop); Warp's loader should load them by full path from the configured ROCm location. `find_host_compiler()` stays untouched for CUDA builds (AMD 1.13 broke it with an undefined `hip_enabled`).
13. **20-CU gfx1151 APU**: shared system memory; no large-memory tests (`test_large.py` tens-of-GiB cases must respect `hipMemGetInfo`); spin-loop starvation (risk 9); GPU-scheduler bugchecks seen on that host under texture and stress workloads in other ports: run Windows validation with known-heavy tests identified up front.
14. **CDNA has no graphics pipeline**: GL interop (`render_opengl.py`) cannot run on gfx90a/942/950; validate it on wave32 Radeon/APU; skip on CDNA by capability query, not by `is_hip`.
15. **CUDA path regressions** (ruling): no auto-selection of HIP, `wp_cuda_device_get_arch` stays `int`, CUDA < 12.3 capture guard untouched, no HIP-motivated workarounds in shared code paths (AMD 1.13's extra syncs in `copy()` and the global per-stream scratch map in `sparse.cu` are not carried).

## Open questions for jeff

Q1. **GPU `tile_fft` for non-power-of-two sizes.** Without libmathdx, upstream's GPU path supports only power-of-two sizes divisible by `block_dim` and raises `ValueError` otherwise (`builtins.py:13435-13448`). ROCm has no device-callable FFT (rocFFT/hipFFT are host-launched). Options: (a) ship 1.14.0+rocm.0 with upstream's no-libmathdx behaviour and name the gap in the release notes; (b) add an in-tree GPU path for non-power-of-two sizes (Bluestein or direct DFT on shared memory) in this line, a new feature upstream does not have. Recommendation: (a) for this line, registered as a deferred candidate, because (b) is new numerical code with no upstream counterpart to carry forward into 1.15..1.19.

Q2. **Value of `__CUDA_ARCH__` under hipRTC.** The ruling has the runtime compiler define what `__CUDA_ARCH__`-gated code needs; Warp's own headers will be HIP-first so the value only affects user/downstream snippets, and any value makes numeric gates in user code (`#if __CUDA_ARCH__ >= 700`) pick a branch that may contain PTX. Recommendation: define it to a low sentinel (e.g. `1`), so numeric user gates fall to their portable non-asm branches, and document it; the porter verifies with a probe that HIP's hipRTC builtin headers do not react to the macro before committing.

Q3. **rocWMMA/MFMA fast path for `tile_matmul` in this line?** The scalar GPU GEMM is correct on both wave widths; an AMD-native path would be faster for larger tiles but needs separate CDNA (MFMA) and RDNA (WMMA) handling. Recommendation: not in 1.14.0+rocm.0; register a deferred candidate for a later line.

Q4. **Conditional graph nodes (`capture_if`/`capture_while` inside a capture).** HIP 7.14 has no conditional node API. Options: (a) report unsupported on HIP exactly as upstream does for CUDA < 12.4 (eager use outside a capture keeps working); (b) emulate (AMD's halo PR #21 does "conditional-graph emulation"), which changes capture semantics. Recommendation: (a), with a deferred candidate to adopt native HIP conditional nodes when ROCm ships them.

Q5. **cuBQL backend on HIP.** Optional, experimental upstream (`bvh_constructor="cubql"`). Recommendation: port it (guards + hipCUB; AMD's 1.13 rewrote it in 26 files, which is reference only); if a construct proves unportable in budget, build with `WP_DISABLE_CUBQL` on HIP so the option raises cleanly, and bring that to you as a deferral rather than deciding it.

Q6. **How a ROCm build is selected.** Upstream auto-detects CUDA; the ruling forbids HIP silently replacing CUDA. Recommendation: an explicit `--hip`/`--rocm-path` option; if both a CUDA Toolkit and HIP are requested, error; if no CUDA Toolkit is found and ROCm is, print a one-line hint to use `--hip` (no silent switch either way). Confirm, since it defines the "documented command" for ruling 5.

Q7. **Clang-CUDA JIT (`warp-clang` NVPTX target, `test_clang_cuda.py`, `--clang-build-toolchain`).** It is an NVIDIA-only alternative to NVRTC; the HIP analogue would be an AMDGPU target in the bundled LLVM, which the packman LLVM build may not include. hipRTC is already clang-based, so HIP gets no capability from it. Recommendation: not ported in this line; the option reports unsupported on HIP devices and the tests skip by capability; registered as a deferred candidate.

Q8. **How the wheel finds ROCm, and CPU-only use.** Upstream's wheel imports on a machine with no NVIDIA driver (driver loaded lazily, CUDA runtime static). HIP's runtime and hipRTC are shared libraries only, and the AOT kernels need `amdhip64` at load. Options: (a) `warp.so` links `amdhip64`/`hiprtc` and the wheel requires a ROCm runtime (system ROCm or TheRock `rocm` wheels), with a clear error when absent; (b) split the HIP code into a second library loaded lazily so CPU-only import still works without ROCm. Recommendation: (a) for this line (as ROCm PyTorch wheels do), documented as a prerequisite and not a pip dependency; (b) as a deferred candidate. Also confirm the default `--offload-arch` list for the release wheel (proposed: gfx90a, gfx942, gfx950, gfx1100, gfx1101, gfx1102, gfx1151, gfx1200, gfx1201).

## Rulings the source qualifies

- Ruling 4 asks for a ROCm equivalent of libmathdx. None exists (no device-callable, LTO-linkable BLAS/solver/FFT on ROCm). Upstream 1.14 already ships cooperative **GPU** implementations for every libmathdx feature when built without it, so the HIP build loses no feature except non-power-of-two GPU FFT (Q1). These are GPU paths, not CPU fallbacks.
- Ruling 2's "the runtime compiler defining what `__CUDA_ARCH__`-gated code needs": defining `__CUDA_ARCH__` alone is not enough and is harmful for Warp's own headers, whose 9 numeric `__CUDA_ARCH__` gates select inline PTX. The plan does both: HIP-first gates in Warp's headers, and a defined `__CUDA_ARCH__` under hipRTC for user code (Q2).
- `__CUDA_ARCH__` in AMD's tree: the IsaacLab correction showed the Newton failure is a guard in Newton's snippet, not `cuda_crt.h:1096`; this plan addresses it from Warp's side as the ruling directs.
