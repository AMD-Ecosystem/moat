# cuda_voxelizer port plan

## Project

- Name: cuda_voxelizer (Forceflow/cuda_voxelizer, Jeroen Baert)
- Upstream: https://github.com/Forceflow/cuda_voxelizer, default branch `main`, planned at `f9fc9a9` ("Removing build badge")
- Fork: https://github.com/AMD-Ecosystem/cuda_voxelizer, port branch `moat-port`
- What it is: a single command-line executable that voxelizes a triangle mesh (read with Trimesh2) on the GPU, with an OpenMP CPU fallback (`-cpu`), and writes .vox / .binvox / .obj / morton blob output. About 1.7k lines; two kernels.
- Planned on windows-gfx1151. There is no lead platform; this plan is arch-independent and every gate validates on its own.

## Existing AMD support

None (intake: `duplicate_effort: none`; no `amd|rocm|hip|gfx` hit in upstream docs, no AMD-Ecosystem/ROCm repo, no community fork found). Upstream is a normal single-author project that accepts PRs (CONTRIBUTING.md exists); it does not run a "link platform forks" policy, so an upstream PR is the right vehicle.

Decision: fresh HIP port. The kernels are plain scalar float geometry plus bitwise atomics -- no tensor cores, no CUTLASS, no warp-level tuning -- so a mechanical HIP port is the right and final form; there is no AMD-native rewrite to consider.

## Build classification

**cmake** (with a second, Visual Studio `.vcxproj` build path; see scope). Evidence:

- `CMakeLists.txt:3` `PROJECT(CudaVoxelize LANGUAGES CXX CUDA)`; `:6` `FIND_PACKAGE(CUDAToolkit REQUIRED)`; `:52-55` the two `.cu` files in `CUDA_VOXELIZER_SRCS_CU`; `:64` links `CUDA::cudart`.
- No `find_package(Torch)`, no `setup.py`/`pyproject.toml`, no Python at all.
- `msvc/vs2022/cuda_voxelizer.vcxproj` is an alternative NVIDIA-only Visual Studio build using the CUDA MSBuild customization.

`ext_type`: `cmake`.

## Port strategy

**Strategy A, shim-header variant.** The sources include CUDA headers by name (`cuda.h`, `cuda_runtime.h`, `device_launch_parameters.h` in `src/voxelize.cuh`, `src/util.h`, `src/util_cuda.h`, `src/libs/cuda/helper_math.h`), so shadow headers in a `hip_compat/` directory, prepended to the include path on the HIP build only, can carry all the aliasing and leave the algorithm sources untouched. The CUDA build never sees the directory.

CMake shape:

- `option(USE_HIP "Build with HIP for AMD GPUs" OFF)`.
- `PROJECT(CudaVoxelize LANGUAGES CXX)`, then `enable_language(HIP)` + `find_package(hip REQUIRED)` under `USE_HIP`, else `enable_language(CUDA)` + `FIND_PACKAGE(CUDAToolkit REQUIRED)` exactly as today.
- `set_source_files_properties(${CUDA_VOXELIZER_SRCS_CU} PROPERTIES LANGUAGE HIP)`; `HIP_ARCHITECTURES "${CMAKE_HIP_ARCHITECTURES}"`. Never pin an arch.
- `target_include_directories(... BEFORE PRIVATE ${CMAKE_SOURCE_DIR}/hip_compat)` for the whole target, because the HOST `.cpp` files (`main.cpp`, `util_cuda.cpp`, `cpu_voxelizer.cpp`, `util_io.cpp`) also include `cuda_runtime.h` and use `float3`, `make_float3`, `checkCudaErrors` and `cudaMallocManaged`.
- Link `hip::host` instead of `CUDA::cudart` (gives host TUs `__HIP_PLATFORM_AMD__` and the HIP include dir).

Why not plain Strategy A with a compat include in every file: the shim keeps `src/*.cu`, `src/*.cuh`, `src/*.cpp` byte-identical except for the genuine correctness fixes below, which is the more mergeable diff.

## CUDA surface inventory

Kernels (2), both grid-stride over triangles, one triangle per thread in practice (`gridSize = ceil(n / blockSize)`):

- `voxelize_triangle` (`src/voxelize.cu`): conservative surface voxelization, `atomicOr` into a 1-bit-per-voxel `unsigned int` table.
- `voxelize_triangle_solid` (`src/voxelize_solid.cu`): Schwarz-Seidel solid voxelization, `atomicXor` into the same table.

Device data / memory:

- `__constant__ uint32_t morton256_{x,y,z}[256]` defined in `src/voxelize.cuh`, which both `.cu` files include; filled with `cudaMemcpyToSymbol`.
- `__device__ size_t debug_d_*` counters, `_DEBUG` only, defined in BOTH `.cu` files under the same names; read with `cudaMemcpyFromSymbol`.
- `cudaMallocManaged` for the triangle buffer (host-filled with `memcpy`) and for the voxel table (kernel atomics, then host read after `cudaDeviceSynchronize`). Never freed (process exit).
- Events for timing; `cudaOccupancyMaxPotentialBlockSize` for launch config; default stream only; `<<<>>>` launches.

Runtime symbols (complete list, incl. helper_cuda.h): `cudaComputeModeProhibited cudaDevAttrClockRate cudaDevAttrComputeCapabilityMajor cudaDevAttrComputeCapabilityMinor cudaDevAttrComputeMode cudaDevAttrIntegrated cudaDevAttrMultiProcessorCount cudaDeviceGetAttribute cudaDeviceProp cudaDeviceSynchronize cudaError cudaErrorInvalidValue cudaError_t cudaEventCreate cudaEventDestroy cudaEventElapsedTime cudaEventRecord cudaEventSynchronize cudaEvent_t cudaGetDevice cudaGetDeviceCount cudaGetDeviceProperties cudaGetErrorName cudaGetErrorString cudaGetLastError cudaMallocManaged cudaMemGetInfo cudaMemcpyDeviceToHost cudaMemcpyFromSymbol cudaMemcpyToSymbol cudaOccupancyMaxPotentialBlockSize cudaSetDevice cudaSuccess` (plus `cudaDeviceReset`/`cudaMemset` if the replacement helper headers or the zeroing fix use them; `cudaHostAlloc`/`cudaMalloc`/`cudaMemcpy` appear only in commented-out code in `main.cpp`). All have direct `hip*` equivalents; `cudaError` (no `_t`, `util_cuda.cpp:9`) needs its own alias. Re-take this list from the swapped-in BSD-3 headers.

Not present (checked): `__shfl*`, `__ballot*`, `warpSize`, `__syncthreads`, `__shared__`, textures/surfaces, streams other than 0, pinned host memory, cuBLAS/cuFFT/cuRAND/cuSPARSE/cuSOLVER/cuDNN, Thrust/CUB/CUTLASS, NCCL, driver API (`cuda.h` is included but no `cu*` call is made), NVRTC/PTX. The only literal 32s are bits-per-`unsigned int` word in `setBit`/`setBitXor`, unrelated to warp width. The port is wavefront-agnostic: identical on wave32 and wave64.

## Risk list

Ordered by likelihood of a silent wrong answer.

1. **Voxel table is never zeroed** (`main.cpp`, `cudaMallocManaged(&vtable, vtable_size)` then straight to the kernel). CUDA hands back zeroed managed pages in practice; ROCm does not promise it ("fresh allocations are not zeroed" fault class). OR/XOR into garbage gives wrong voxels with no error. Fix: `cudaMemset(vtable, 0, vtable_size)` after the allocation. Unconditional is correct on CUDA too (the spec does not promise zero); it is a separate small commit so the reviewer can judge it alone.
2. **Bitwise atomics on managed memory.** `atomicOr`/`atomicXor` target a `hipMallocManaged` buffer. On a discrete PCIe card without XNACK, managed memory can be host-resident fine-grained memory, and PCIe AtomicOps cover only add/swap/CAS -- the cudaKDTree port measured int `atomicMin`/`atomicMax` on a default `hipMallocManaged` buffer being silently dropped on gfx90a while `atomicAdd`/`atomicCAS` worked. OR/XOR are in the unsupported set. This is the most likely gfx90a (wave64 gate) failure. The CPU-vs-GPU diff below catches it. Fix if it fires: allocate the voxel table with `cudaMalloc` + `cudaMemset` and copy it back with `cudaMemcpy` before file output (works on CUDA too; guard on the HIP build only if the reviewer wants the CUDA path byte-identical). Probe this early on the wave64 host rather than at validation.
3. **Managed memory on Windows.** HIP docs mark `hipMallocManaged` "under development" on Windows. On gfx1151 (APU, system memory) it may simply work, may fail allocation (then `checkCudaErrors` exits -- loud), or may behave as host-pinned. Same fallback as risk 2 removes the dependency entirely; if risk 2 forces the device-memory path, prefer applying it to both buffers on the HIP build so Windows and Linux share one code path.
4. **`helper_math.h` under HIP.** (a) Its `#ifndef __CUDACC__` block defines host `fminf`/`fmaxf`/`min`/`max`/`rsqrtf`; HIP-clang does not define `__CUDACC__`, so in the `.cu` TUs these collide with HIP's `__host__ __device__` math. Extend the guard to `!defined(__CUDACC__) && !defined(__HIPCC__)`. (b) HIP's `float2/float3/int3` are `HIP_vector_type` with their own non-template friend operators; helper_math's same-signature `operator+(float3, float3)` etc. can become ambiguous on host and device. If the compiler reports ambiguity, skip exactly the colliding operator definitions on HIP; keep `dot`, `cross`, `normalize`, `clamp`, the vector `fminf`/`fmaxf` and the scalar-mixing operators. Check `-o obj` output still matches CPU after any change here, because these operators are the whole geometry.
5. **Header guards in `helper_cuda.h`.** `_cudaGetErrorEnum(cudaError_t)`, `checkCudaErrors` and `getLastCudaError` are inside `#ifdef __DRIVER_TYPES_H__`; `findCudaDevice`/`gpuGetMaxGflopsDeviceId` inside `#ifdef __CUDA_RUNTIME_H__`. Those macros come from NVIDIA's headers, so under the HIP shim the whole API vanishes and every `checkCudaErrors` is undeclared. The shim `cuda_runtime.h` defines both macros after including `hip/hip_runtime.h` (verify the swapped-in BSD-3 version uses the same guards). `helper_cuda.h` is included by relative path (`"libs/cuda/helper_cuda.h"`), so it cannot itself be shadowed.
6. **`__constant__` / `__device__` variables defined in a header included by two TUs.** nvcc gives each non-RDC TU a private copy; HIP-clang's host-side shadow variables may collide at link (`multiple definition of morton256_x`). Same for the `_DEBUG` counters (Debug builds only). Fix if the link fails: `static __constant__` / `static __device__` -- valid and behaviour-identical on CUDA too. Also exercise a Debug configure once so the `_DEBUG` symbols are covered.
7. **AMD compute capability is not NVIDIA's.** `initCuda` rejects `major < 2` (AMD reports gfx major 9/11/12 -- passes). `helper_cuda.h` `_ConvertSMVer2Cores` prints "MapSMtoCores for SM 11.5 is undefined" on AMD; cosmetic, single-device selection is unaffected. Do not add CC-keyed logic.
8. **FP contraction.** clang HIP contracts FMAs across expressions (`-ffp-contract=fast`), nvcc and the host compiler do not to the same degree; the plane/edge tests are sign tests on float sums, so a boundary voxel can flip between GPU and CPU. If the GPU-vs-CPU diff is non-zero, rebuild the HIP TUs with `-ffp-contract=off`: a diff that vanishes is FP reassociation (record it, do not ship a flag change without the reviewer's view); one that persists is a real bug.
9. **Out-of-bounds writes** (AMD faults where CUDA tolerates): morton index is only in range for power-of-two grid sizes (upstream documents `-s` as a power of 2); solid-mode `xmax` from `get_x_coordinate` is derived from float division. Test only power-of-two sizes for morton; run the solid case at several sizes and watch for memory faults.
10. **Upstream behaviour kept as-is:** `voxelize_triangle_solid` uses `return` (not `continue`) for a degenerate normal inside the grid-stride loop; harmless with one triangle per thread. Not a port issue; do not change.
11. **Windows toolchain** (windows gate): CMake HIP on Windows wants every language on the GNU-driver `clang++` (clang-cl host + HIP fails, see the skill's validation reference). With HIP sources the executable links through the HIP link rule, which on Windows mangles MSVC-style flags: either set `LINKER_LANGUAGE CXX` (objects are non-RDC, so the device code is already embedded; link `hip::host`) or vendor `cmake/hip_link_win.py` from the skill's assets, guarded to `WIN32`. `FIND_PACKAGE(OpenMP REQUIRED)` with clang on Windows needs `libomp`; check what the ROCm SDK ships before reaching for MSVC's `vcomp`. Trimesh2 must be built with a CRT compatible with the port (`/MD`); building its `libsrc` with the same clang avoids a mismatch. `char *OutputFormats[] = {"..."}` in `main.cpp` is a warning under clang, not an error -- leave it.
12. **Rule-of-five / textures / 256-B pitch / warp size**: not applicable (no handles in classes, no textures, no warp intrinsics).

## Build commands

Trimesh2 (all platforms; same tag upstream CI uses):

```
git clone --depth 1 -b 2022.03.04 https://github.com/Forceflow/trimesh2.git ../trimesh2
make -C ../trimesh2 -j"$(nproc)" all     # upstream CI; needs mesa-common-dev libglu1-mesa-dev libxi-dev for the GL utilities
```

(Only `libtrimesh.a` in `lib.Linux64/` is needed; building just `libsrc` avoids the GL packages.)

Linux, wave64 (gfx90a) / wave32 (gfx1100 etc.):

```
cmake -S . -B build-hip -G Ninja -DUSE_HIP=ON \
  -DCMAKE_HIP_ARCHITECTURES=gfx90a -DCMAKE_PREFIX_PATH=/opt/rocm \
  -DCMAKE_BUILD_TYPE=Release \
  -DTrimesh2_INCLUDE_DIR=../trimesh2/include \
  -DTrimesh2_LINK_DIR=../trimesh2/lib.Linux64
cmake --build build-hip -j"$(nproc)"
```

Windows (gfx1151; TheRock SDK, source `agent_space/win_rocm_env.sh`): same configure with `-DCMAKE_HIP_ARCHITECTURES=gfx1151`, all compilers set to the SDK's `clang++`, Trimesh2 `libsrc` built with the same compiler; stage `amdhip64_7.dll`, `rocm_kpack.dll`, `amd_comgr*.dll` next to `cuda_voxelizer.exe` (`rocm_stage_runtime`).

CUDA no-regression (where nvcc exists): the unchanged upstream recipe, `cmake -S . -B build-cuda -DTrimesh2_INCLUDE_DIR=... -DTrimesh2_LINK_DIR=...` with `CUDAARCHS=60`, must still configure and build; `USE_HIP` defaults OFF.

## Test plan

Upstream has no test suite. Its CI runs one smoke test, `./build/cuda_voxelizer -f ./test_models/bunny.OBJ -s 64 -cpu`, which never touches the GPU. The GPU evidence is therefore a GPU-vs-CPU differential on the same binary: the CPU voxelizer (`cpu_voxelizer.cpp`) implements the same algorithms independently and is the oracle.

Matrix, on `test_models/bunny.OBJ` (copy the model to a scratch dir first; outputs are written beside it as `<base>_<size>...` and the GPU and CPU runs overwrite each other, so rename between runs):

- modes: surface (default), `-solid`
- sizes: 64, 256, 512 (power of two)
- formats: `-o binvox`, `-o morton` (exercises the `__constant__` LUT path and `cudaMemcpyToSymbol`), `-o obj_points`; one `-o vox` and one `-o obj` run for the writers

For each (mode, size, format): run GPU (no flag; the log must show `## GPU VOXELISATION` and `[Perf] Voxelization GPU time`, never "Falling back to CPU"), then `-cpu`, then compare. `binvox` and `morton` are compared bit-for-bit as voxel sets (decode binvox RLE, or `cmp` the morton blob); report the number of differing voxels and the total filled. Pass = 0 differing voxels. A non-zero count goes through risk 8's `-ffp-contract=off` triangulation before any verdict, and the count, sizes and outcome go in notes.md.

Also:

- Repeat GPU runs 3x at 512 surface + solid: outputs must be identical run to run (atomics are order-independent).
- One Debug-configured build (`-DCMAKE_BUILD_TYPE=Debug`) links and runs at 64 (covers the `_DEBUG` `__device__` counters and `cudaMemcpyFromSymbol`).
- Non-GPU regression set: the upstream CI smoke command (`-s 64 -cpu`) passes in the HIP build, and CPU output is unchanged from a CPU run of an unmodified upstream build where one is available.
- Wave64 gate (gfx90a discrete) is where risk 2 bites; wave32 and windows gates run the identical matrix.

## Open questions

1. **Scope of the Visual Studio project (ruled by jeff 2026-11-03: CMake-only).** `msvc/vs2022/cuda_voxelizer.vcxproj` is a second, NVIDIA-only build path that relies on the CUDA MSBuild customization. The plan ports the CMake build (which already covers Windows, and is how upstream's own Windows CI builds) and leaves the `.vcxproj` untouched, recorded as `scoped_out` in surface.json. The program itself is ported in full; this is a build-path cut, not a component cut, but it is a cut, jeff confirmed the cut on 2026-11-03: the port is CMake-only and the `.vcxproj` stays untouched.
2. **The fork's mirror branch already hosts the EULA-vintage headers.** The counsel ruling in `deferred.json` says to swap `helper_cuda.h`/`helper_string.h` for the BSD-3 versions "at the tip BEFORE any fork is created; never host the proprietary vintage at our tip". The fork now exists and its `main` (an unmodified upstream mirror, `f9fc9a9`) carries the old headers. The plan makes the swap the first `moat-port` commit, so the port tip is clean; whether the mirror `main` is acceptable under the ruling is a person's call.
3. Whether the voxel-table zeroing (risk 1) and any `static __constant__` change should be unconditional or `USE_HIP`-guarded is left to review; both are correct on CUDA.
