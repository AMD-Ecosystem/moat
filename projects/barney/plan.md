# barney -- port plan (Linux gfx90a lead)

## Project
- Name: barney
- Upstream: https://github.com/NVIDIA/barney (default branch `main`, clone at commit fe10e5d)
- A scalable, optionally data-parallel ANARI multi-GPU path tracer. Apache-2.0 throughout (cleared, see notes.md). depends_on cuBQL (MOAT cuBQL `completed` on gfx90a -> satisfied).

## Existing AMD support
NONE. Checks run:
- `grep -rniE 'amd|rocm|hip|gfx[0-9]'` over README*, doc/, CONTRIBUTING.md -> zero hits.
- Web search ("barney ANARI AMD ROCm HIP HIPRT") -> only NVIDIA/barney and ingowald/barney (the author's personal mirror, same CUDA/OptiX code, no AMD path). No ROCm-org port, no separately-named AMD project, no rocm.docs.amd.com page, no upstream rocm/hip branch or PR.
Decision: genuine from-scratch HIP port. No authoritative AMD effort to adopt or improve. We add TWO new AMD backends and leave OptiX/Embree/CUDA paths byte-identical.

## Build classification
- pure CMake. Top-level `CMakeLists.txt:31` `project(... LANGUAGES C CXX)`, then conditional `enable_language(CUDA)` (`CMakeLists.txt:56`) gated by `check_language(CUDA)`; backends chosen by `BARNEY_BACKEND_OPTIX/CUDA/EMBREE` options (`CMakeLists.txt:131-139`). No `find_package(Torch)`, no setup.py/pyproject. -> Strategy A (CMake compat-header + `LANGUAGE HIP`), exactly like cuBQL and colmap.
- ext_type set to `cmake` in upstream.json/status.json.

## Architecture recap (decides the whole plan)
barney isolates all ray-tracing into `rtcore/` behind three interfaces (`rtcore/TraceInterface.h`, `ComputeInterface.h`, `AppInterface.h`) that `#include` the active backend's header by `BARNEY_RTC_<BACKEND>` macro. Backends today: `optix` (HW-RT via OWL/OptiX), `embree` (CPU), `cuda`+`cudaCommon` (OptiX-free SOFTWARE BVH via cuBQL). The main `barney/` library is compiled ONCE PER BACKEND (`barney_cuda`/`barney_optix`/`barney_backend_embree`), and the SAME barney sources (`HOST_SOURCES` + `DEVICE_PROGRAM_SOURCES`, the 12 `*.dev.cu` geometry/volume programs) are recompiled against each backend's `rtcore` headers. The ANARI library `anari_library_barney` links one of those backend libs.

Program model -- CRITICAL: barney's `cuda` backend is a MEGAKERNEL software tracer. Per-geometry closest-hit / any-hit / intersect programs are stored as DEVICE FUNCTION POINTERS in the SBT (`rtcore/cuda/Geom.h:21-36` `SBTHeader{ AHProg ah; CHProg ch; ... IntersectProg intersect; }`) and called directly inside `TraceInterface::traceRay` (`rtcore/cuda/TraceInterface.h:166,171,205`). The whole device program set is linked with `-rdc=true`/`CUDA_RESOLVE_DEVICE_SYMBOLS` so function-pointer dispatch resolves. There is NO PTX/SBT pipeline in the cuda backend; OWL/OptiX is used only by the optix backend (PTX via `embed_ptx`, `rtcore/optix/Device.cpp`).

## Port strategy -- TWO AMD backends, sequenced

### Backend 1 (DO FIRST, lower risk): `rtcore/cuda` + `rtcore/cudaCommon` -> HIP (software BVH on cuBQL)
A direct compute port, the cuBQL pattern. The cuda backend already does its own software BVH traversal and runs the same megakernel on any HIP device; it needs NO HIPRT, NO hardware RT. This is the primary deliverable and the one validated first on gfx90a.

Approach (Strategy A):
1. Add a compat header `rtcore/cudaCommon/cuda_to_hip.h` (the ONLY file that knows HIP). On `USE_HIP`/`__HIP_PLATFORM_AMD__` include `<hip/hip_runtime.h>` and alias the cuda spellings these files actually use; else include `<cuda_runtime.h>`. Include `<cstring>`/`<cstdlib>` BEFORE the hip runtime (gpuRIR lesson: host memcpy/memset resolving to device overloads).
   - barney's macro `BARNEY_CUDA_CALL(call) -> BARNEY_CUDA_CHECK(cuda##call)` (`cuda-helper.h:59`) is the SAME token-paste pattern cuBQL used (`CUBQL_CUDA_CALL`). The alias set must cover every `cuda##X` site: Malloc, Free, Memcpy, MemcpyAsync, Memset/MemsetAsync, StreamCreateWithFlags (+`cudaStreamNonBlocking`), StreamSynchronize, SetDevice, GetDevice, DeviceSynchronize, GetLastError, GetErrorString, CreateTextureObject, DestroyTextureObject, Malloc3DArray/MallocArray, Memcpy3D/Memcpy2DToArray, plus the texture/array enums and `cudaResourceDesc`/`cudaTextureDesc`/`cudaChannelFormatDesc`/`cudaArray_t`/`cudaTextureObject_t` types. Grep `rtcore/cudaCommon` + `rtcore/cuda` for `cuda` to enumerate exhaustively (Texture.cu, TextureData.cu, Device.cu both dirs).
   - `cuda_common.h:8` hardcodes `#include <cuda_runtime.h>` and `:9-12` `#ifdef __CUDACC__ -> <cuda/std/limits>, <cuda.h>` -- route these through the compat header (HIP has no `<cuda/std/limits>`; use `<limits>`; drop `<cuda.h>` driver header on HIP unless a driver call is actually used).
2. CMake: in `rtcore/CMakeLists.txt` add a `USE_HIP` path mirroring the `BARNEY_BACKEND_CUDA` block. Mark `cudaCommon/*.cu` and `cuda/*.cu` `LANGUAGE HIP` and set `HIP_ARCHITECTURES ${CMAKE_HIP_ARCHITECTURES}` (NEVER a literal gfx90a in source; default to gfx90a only when unset, per guide). Top-level `CMakeLists.txt`: add a `BARNEY_DISABLE_CUDA`-parallel HIP discovery so `enable_language(HIP)` happens and `BARNEY_HAVE_CUDA`-equivalent paths (cuBQL subproject, `barney_cuda` instantiation, `.cu` compile flags) are reachable on the HIP build. Consume cuBQL per its notes "Install as a dependency": `set(CUBQL_USE_HIP ON)` + `set(CMAKE_HIP_ARCHITECTURES ...)` before `add_subdirectory(submodules/cuBQL)`, and link `cuBQL` + `cuBQL_cuda_float3`/`_static` (barney links `cuBQL_cuda_float3_static`, `barney/CMakeLists.txt:132,210`). Clone AMD-Ecosystem/cuBQL @ moat-port into `_deps/cuBQL` (gitignored) and point `BARNEY_USE_EXTERNAL_CUBQL`/the subdir at it for the build.
3. The `barney/CMakeLists.txt` per-backend instantiation: add a `barney_hip` (or fold into the cuda instantiation under HIP) compiling `HOST_SOURCES`+`DEVICE_PROGRAM_SOURCES` against the HIP rtcore. The `-rdc=true`+`CUDA_RESOLVE_DEVICE_SYMBOLS` properties become the HIP equivalents (`-fgpu-rdc` + a device-link step, or rely on hipcc whole-program). VERIFY device-function-pointer dispatch links and runs (this is the megakernel's whole correctness basis; cuBQL's s07 proved hipMemcpyFromSymbol/function-pointer dispatch works on gfx90a/ROCm 7.2.1).
4. `--expt-relaxed-constexpr`/`--extended-lambda` are nvcc flags (`barney/CMakeLists.txt:13,141`, used by the cuda backend's extended lambdas in TraceInterface). hipcc/clang accepts relaxed-constexpr and extended lambdas by default; gate those flag injections under `$<COMPILE_LANGUAGE:CUDA>` only (they already are) so the HIP TU does not receive unknown nvcc flags.

Naming: the new backend implements the SAME `rtc::cuda`-namespace interface barney expects, OR introduces a parallel `rtc::hip` namespace. Prefer REUSING the `cuda` backend source under a `USE_HIP` build of the existing files (smallest diff, byte-identical CUDA path) rather than copying to a new `rtcore/hip/` dir -- the files are already backend-generic compute. Decision for porter: try the in-place `USE_HIP` route first; only fork to `rtcore/hip/` if a clean separation is forced.

### Backend 2 (DO SECOND, higher risk): NEW `rtcore/hiprt` -- hardware-RT via AMD HIPRT
A new sibling backend mirroring `rtcore/optix` structure, mapping to HIPRT. Software BVH traversal on gfx90a (no HW RT units on CDNA2 -- validatable on THIS host), hardware-accelerated traversal on RDNA2+ (gfx1100/gfx1201 followers).

PRECEDENT -- MOAT has already done an OptiX->HIPRT reimplementation. EnvGS Stage 2 (`projects/EnvGS/notes.md` "## Stage 2 port: OptiX -> HIPRT"; code in `projects/EnvGS/src/submodules/diff-surfel-tracing/hiprt_tracer/`) was MOAT's FIRST OptiX->HIPRT port and is VALIDATED on gfx90a (ROCm 7.2.1). It establishes the validated mapping, the HIPRT-from-source build, and two fault-class lessons reused below. LICENSE NOTE: EnvGS upstream is a non-commercial Inria license, so it is used here ONLY as a TECHNICAL REFERENCE for the OptiX->HIPRT technique and the AMD-authored HIPRT/Orochi glue patterns (general HIPRT API usage). NO EnvGS surfel/rasterizer geometry code is copied; barney's hiprt backend is written fresh against barney's own geometry/scene types.

VALIDATED OptiX->HIPRT mapping to reuse (EnvGS Stage 2, mapped onto barney's `rtcore/optix` Device/Geom/Group/Buffer/Denoiser/TraceInterface surface):
- triangle GAS `optixAccelBuild` / `OPTIX_BUILD_INPUT_TYPE_TRIANGLES` -> `hiprtCreateGeometry` + `hiprtBuildGeometry` over a `hiprtTriangleMeshPrimitive` (barney `rtcore/hiprt/Group.cpp` / `Geom.cpp`). EnvGS uses `hiprtBuildFlagBitPreferFastBuild` and a reused temp buffer with `hiprtBuildOperationUpdate` for refit -- the same build/refit split barney's `Group` needs.
- raygen + closesthit + miss COLLAPSE to ONE HIP kernel (the megakernel). EnvGS proved the OptiX raygen/CH/miss split is unnecessary on HIPRT -- one launched kernel does traversal + shading. This is exactly barney's existing megakernel shape (see below).
- `__anyhit__` record-and-ignore -> a HIPRT FILTER FUNCTOR that records the hit into a per-ray payload and returns true (reject) so the AnyHit traversal enumerates EVERY hit along the ray, t-sorted (EnvGS `surfelFilter` in `hiprt_tracer/kernels.h`; registered by name via `hiprtFuncNameSet.filterFuncName` + `hiprtCreateFuncTable`/`hiprtSetFuncTable`). barney's any-hit programs (transparent/clip geometry) map onto this filter-functor pattern one-for-one.
- `optixLaunch` -> `oroModuleLaunchKernel` of a kernel JIT-built by `hiprtBuildTraceKernels` (Orochi/hiprtc), with a HIPRT disk cache (`hiprtSetCacheDirPath`). EnvGS self-JITs `kernels.h` from a vendored HIPRT SDK at runtime; barney can JIT or (preferred, see HIPRT-dependency note) link a precompiled trace kernel.
- Orochi context binding: bind Orochi to the SAME HIP context the host runtime already made current (`oroCtxGetCurrent`, fallback `oroDevicePrimaryCtxRetain`), so the BVH build and trace kernels see the host's device pointers. EnvGS notes a silent failure mode (degenerate BVH / zero hits) if the build runs in a fresh context -- relevant if barney's hiprt Device creates its own Orochi context rather than adopting the cuda_common HIP Device's.

File layout (mirror `rtcore/optix/`, 13 files):
- `rtcore/hiprt/Device.{h,cpp}` -- create `hiprtContext` (over the cuda_common HIP Device's `hipStream_t`/device); `buildPipeline()`/`buildSBT()` -> build HIPRT trace kernels via `hiprtBuildTraceKernels`/`hiprtBuildTraceKernelsFromBitcode`; `createBuffer/Group/Geom/GeomType/Denoiser`.
- `rtcore/hiprt/Geom.{h,cpp}` + `GeomType` -- `hiprtTriangleMeshPrimitive` for triangles; `hiprtAABBListPrimitive` + a custom-function intersection for user geoms (spheres/cylinders/cones/capsules).
- `rtcore/hiprt/Group.{h,cpp}` -- `hiprtGeometry` (BLAS) build/refit via `hiprtBuildGeometry`; `hiprtScene` (TLAS) with `hiprtFrameMatrix`/instance transforms via `hiprtBuildScene`. `getDD()` returns the `hiprtScene` handle as the `rtc::AccelHandle`.
- `rtcore/hiprt/TraceInterface.h` -- device-side: implement the SAME `rtc::TraceInterface` methods (getPrimitiveIndex/getGeometryIndex/getInstanceID/getRayTmax/getWorldRayOrigin/transform*/traceRay/...) on top of HIPRT device traversal (`hiprtGeomTraversalClosest`/`hiprtSceneTraversalClosest` and the custom-function table). This replaces the optix device intrinsics (optixTrace, optixGetPrimitiveIndex, etc) one-for-one; the `TraceInterface.h` dispatch header gains a `#if BARNEY_RTC_HIPRT -> rtcore/hiprt/TraceInterface.h` arm.
- `rtcore/hiprt/Buffer.{h,cpp}`, `AppInterface.h`, `ComputeInterface.h` -- reuse `cudaCommon` (HIP) like optix reuses cudaCommon; HIPRT shares the HIP runtime so `cuda_common::Device`/Texture/Buffer are the base.
- `rtcore/hiprt/Denoiser.{h,cpp}` -- see denoiser substitution below.

Program / SBT model (the hard design decision):
- OptiX backend: programs -> PTX (`embed_ptx`) -> OWL pipeline + SBT. HIPRT does NOT use an OptiX-style SBT; it uses bitcode-linked trace kernels and a 2-D CUSTOM FUNCTION TABLE indexed by (rayType, geomType) (HIPRT v2 `hiprtBuildTraceKernelsFromBitcode`). For barney's per-geometry CH/AH/intersect this means: compile barney's `DEVICE_PROGRAM_SOURCES` to bitcode, expose the intersect/CH/AH entry points as HIPRT custom functions, and let HIPRT link them into the trace kernel.
- SIMPLER first-cut alternative the porter should weigh (RECOMMENDED, now reinforced by EnvGS precedent): barney's cuda megakernel ALREADY implements the full traversal + per-geom function-pointer dispatch in software and runs on gfx90a. For the hiprt backend's FIRST correctness milestone, use HIPRT ONLY for BVH BUILD + the box/triangle traversal kernel, and keep barney's existing function-pointer CH/AH/intersect dispatch (megakernel style) rather than HIPRT's custom-function-table SBT. That decouples "get HW-RT BVH working" from "port the SBT/program-linking model" and is the lower-risk path to a validated gfx90a result. Full HIPRT-native SBT (bitcode custom functions) is a follow-up once correctness holds. Record which model is shipped in notes.md.
- HOW EnvGS's mapping lands on barney's megakernel (reconciliation, concrete). EnvGS's "collapse raygen/CH/miss to one kernel + a filter functor" IS a megakernel, so it maps cleanly onto barney's. Spell-out for the porter:
  - barney's single `TraceInterface::traceRay` megakernel stays the one launched HIP kernel. Inside it, replace ONLY the BVH traversal core (today: barney's software cuBQL `shrinkingRayQuery` walk) with a HIPRT traversal object (`hiprtGeomTraversalClosest`/`hiprtGeomTraversalAnyHit` over the built `hiprtGeometry`/`hiprtScene`). EnvGS uses the AnyHit-traversal-with-always-reject-filter form to enumerate all hits; barney's closest-hit geometry uses `...Closest`, and barney's any-hit geometry (transparent/clip) uses the AnyHit+filter form -- both available.
  - barney's 12 `*.dev.cu` programs (CH/AH/intersect per geom type) DO NOT each become a HIPRT custom-function-table entry in the first cut. Keep barney's device-function-pointer SBT dispatch: after HIPRT returns a hit (primID/instID/t/uv), call barney's existing `SBTHeader.ch`/`.ah`/`.intersect` function pointer exactly as the cuda backend does today (`rtcore/cuda/TraceInterface.h:166,171,205`). HIPRT supplies the hit; barney's megakernel supplies the shading dispatch. This is the minimal-risk shape and matches what EnvGS shipped (one kernel, hits via HIPRT, shading in-kernel).
  - For barney's CUSTOM geometries (spheres/cylinders/cones/capsules: `hiprtAABBListPrimitive`), HIPRT needs a per-primitive intersection callback in its func table even in the first cut (triangles do not). Either register a thin HIPRT intersect functor that calls barney's existing `.intersect` program, or build those geoms as their cuBQL-traversed path on the hiprt backend too (the box/AABB traversal barney already has). Porter decides at first compile; recommend the func-table intersect-thunk so all geometry rides HIPRT's BVH.
  - DEFER, do not adopt first: moving barney's 12 programs to HIPRT's native 2-D custom-function-table (rayType x geomType) bitcode SBT. It is the "more native" end state but is the costly part EnvGS did NOT need. Register as a deferred enhancement once the megakernel cut validates.

### Denoiser substitution
OptiX provides `OptixDenoiser` (`rtcore/optix/Denoiser.cpp`, optix>=8). HIPRT has NO denoiser. Options, in order of preference:
1. Mirror barney's OWN cuda backend: `rtc::cuda::Denoiser` is a NO-OP passthrough (`rtcore/cuda/Device.h:72-86` resize() just stores dims, run() does nothing, `createDenoiser()` returns nullptr in Device.cu). The hiprt backend can ship the same no-op denoiser for the first validated milestone -- barney already runs un-denoised on the cuda backend. This is the safe default.
2. If GPU denoising is wanted later: barney already integrates OIDN (`BARNEY_OIDN_GPU`, CMakeLists.txt:157-167). OIDN has a HIP/ROCm device. Wire the hiprt (and hip-compute) backend's denoiser to OIDN-GPU on ROCm. Register this as a deferred enhancement (utils/deferred.py) -- not required for the port's correctness gate.
Decision: ship the no-op denoiser (option 1) for both AMD backends' first validation; note OIDN-GPU as deferred.

### CMake wiring (both backends)
- New options mirroring the existing switches: `BARNEY_BACKEND_HIPRT` (and the compute backend either reuses `BARNEY_BACKEND_CUDA` under `USE_HIP` or a `BARNEY_BACKEND_HIP`). Add to the backend-select block (`CMakeLists.txt:128-139`) and the `barney_rtc` aggregation (`rtcore/CMakeLists.txt:246-255`).
- HIPRT discovery: `find_package(hiprt)` / a `Findhiprt.cmake` locating the SDK (headers + `libhiprt*.so` + the precompiled HIPRT bitcode). Pin the version via a `BARNEY_HIPRT_DIR`/`hiprt_ROOT` cache var. Define `BARNEY_RTC_HIPRT=1` on the hiprt libs like `BARNEY_RTC_OPTIX=1`.
- Arch NEVER hardcoded: drive everything off `-DCMAKE_HIP_ARCHITECTURES` (default gfx90a only when unset). A lead bring-up should configure `-DCMAKE_HIP_ARCHITECTURES="gfx90a;gfx1100"` to catch wave-size issues early (guide: multi-arch IS the warp-size test), though barney's GPU path uses no warp intrinsics so the risk is low.

## HIPRT dependency acquisition (load-bearing -- pin and verify gfx90a)
HIPRT is a NEW external dependency, NOT a submodule of barney. GPUOpen's consumer page lists only RDNA2+ for HARDWARE RT and does not advertise CDNA/gfx90a; the user has VERIFIED HIPRT runs on gfx90a via its SOFTWARE BVH traversal path (HIPRT falls back to a HIP shader BVH on any HIP device without RT units). Because the marketing does not promise gfx90a, the porter MUST pin a specific HIPRT version and VERIFY at build time that it produces a working gfx90a code object before relying on it.
Obtain (porter, in order):
1. Prefer building from source: `git clone --recursive https://github.com/GPUOpen-LibrariesAndSDKs/HIPRT` into `_deps/HIPRT` (gitignored), build against the host ROCm (`/opt/rocm`, ROCm 7.2.1) with its CMake/Premake path. Source build lets us target gfx90a explicitly and inspect the software-fallback path.
2. Fallback: prebuilt binaries from gpuopen.com/hiprt if the source build is problematic, but confirm the prebuilt ships a gfx90a-capable software path (the precompiled HIPRT bitcode must cover gfx90a or be recompilable for it).
3. VERIFY gfx90a at build time: build a tiny HIPRT smoke (build a geometry + scene, trace one ray) on gfx90a and confirm a correct hit BEFORE porting barney's geometry onto it. If HIPRT cannot target gfx90a on our stack, the hiprt backend is BLOCKED for gfx90a (validate it on the RDNA followers instead) -- but Backend 1 (the cuBQL software-compute backend) still delivers a full validated AMD port on gfx90a independently. Record the pinned HIPRT commit/version + ROCm version in notes.md.
EnvGS Stage 2 from-source recipe (PROVEN on gfx90a, ROCm 7.2.1) -- reuse it:
- Build HIPRT from source with BITCODE OFF, targeting the wanted version: `cmake -DBITCODE=OFF` then `--target hiprtNNNNN` (EnvGS built `hiprt03001` into `third_party/hiprt/dist/bin/Release`). `-DBITCODE=OFF` builds the HIP-shader/software-traversal path (the one that runs on gfx90a, which has no RT cores); this is what de-risks gfx90a. Do NOT commit the resulting `libhiprtNNNNN.so` (the `.so` is gitignored / not a PR artifact).
- Self-JIT-from-vendored-SDK option: EnvGS vendors the HIPRT SDK and JITs `kernels.h` at runtime via `hiprtBuildTraceKernels` (Orochi -> hiprtc) with a disk cache (`hiprtSetCacheDirPath`). barney CAN do the same (JIT a trace kernel from source at Device init) -- but see the linking assessment below; for barney a precompiled-link path is likely cleaner than self-JIT.
- Standalone-glue-static-lib + POD/void* boundary pattern (EnvGS `hiprt_tracer/hiprt_wrapper.{h,cpp}`): EnvGS put ALL HIPRT/Orochi code in a STANDALONE static lib whose ONLY exposed interface is plain C++/POD/raw-device-pointer/stream-as-void* entry points (build-geometry, launch); no HIPRT or Orochi type crosses the boundary. WHY EnvGS needed it: Orochi's hipew driver loader REDECLARES the HIP driver API and conflicts with torch's `<hip/hip_runtime.h>` -- the two cannot share a TU, so the torch TU reaches HIPRT only through the void* wrapper.
- ASSESSMENT for barney (porter to confirm): barney is HIPCC-NATIVE (Strategy A, a pure CMake/hipcc build, NOT a torch CUDAExtension). The hipew-vs-torch-`hip_runtime.h` collision that FORCED EnvGS's void* boundary very likely DOES NOT apply to barney -- there is no torch runtime header to clash with. So barney can probably link `libhiprt` DIRECTLY into the hiprt backend (include `<hiprt/hiprt.h>` in `rtcore/hiprt/*.cpp`, link `libhiprtNNNNN.so`), and may not need Orochi at all if it uses the HIP runtime API barney already has rather than Orochi's driver loader. Two outcomes, porter picks at first compile: (a) PREFERRED -- direct `find_package`/link of libhiprt, no Orochi, no void* wrapper, HIPRT trace kernel either precompiled or JIT'd via hiprtc directly; (b) FALLBACK -- if HIPRT's runtime-kernel build genuinely pulls Orochi/hipew and it clashes with barney's hipcc HIP headers in a shared TU, replicate EnvGS's standalone-static-lib + POD/void* boundary to isolate it. State the chosen path in notes.md.
The hiprt SDK is NOT vendored into barney for the upstream PR: add it as a discovered dependency (Findhiprt.cmake + a documented `hiprt_ROOT`), the same way barney finds OptiX (`OptiX_INSTALL_DIR`) and OIDN -- so the PR carries no large binary blob.

## Risk list (fault classes, ranked)
1. HIPRT SBT/program model vs barney's function-pointer megakernel (HIGH, Backend 2). OptiX's PTX-pipeline+SBT and HIPRT's bitcode + 2-D custom-function-table are BOTH different from barney's cuda megakernel device-function-pointer dispatch. Mitigation: first-cut hiprt backend keeps barney's megakernel CH/AH/intersect dispatch and uses HIPRT only for BVH build+traversal (see Backend 2). Full HIPRT-native custom-function SBT is a deferred follow-up.
2. HIPRT gfx90a support (was vendor-unconfirmed; now DE-RISKED, MED, Backend 2). PROVEN on gfx90a by MOAT's EnvGS Stage 2 (a full OptiX->HIPRT tracer validated on gfx90a / ROCm 7.2.1 via HIPRT's `-DBITCODE=OFF` software-traversal path). This is no longer an open unknown. Still pin the specific HIPRT version and run the build-time smoke (gpuOpen does not advertise CDNA, and the version/ROCm combo must be reconfirmed on barney's stack), but treat gfx90a as expected-to-work, not a gating risk. Backend 1 remains the independent gfx90a deliverable regardless.
3. Denoiser absence in HIPRT (MED). Mitigation: no-op denoiser (matches barney's cuda backend), OIDN-GPU deferred.
4. Texture fault classes (MED, both backends) -- AMD-strict cases from the guide that barney's texture code can hit:
   - `cudaFilterModeLinear` + element-read float textures REJECTED on ROCm (popsift). barney's default `TextureDesc.filterMode = FILTER_MODE_LINEAR` (rtcore-common.h:66) over float volume textures -> hipCreateTextureObject may fail. Mitigation: point-filter + software bilinear/trilinear in the `tex2D/tex3D` wrappers (ComputeInterface.h), -0.5 texel-center convention.
   - 256B texture pitch alignment on gfx90a (colmap/CV-CUDA). barney uses cudaArray-backed textures (resType Array, Texture.cu:44) not pitch2D, so likely N/A -- but confirm TextureData.cu array allocs.
   - Layered-array collapse (popsift/clr#275): barney's 3D textures use real 3D arrays (Malloc3DArray), not `cudaArrayLayered` -- confirm no layered arrays in TextureData.cu (low risk).
5. Rule-of-five on resource handles (MED). `rtc::cuda_common::Texture`/`TextureData` dtors call DestroyTextureObject/free; `Group` dtors free BVH/SBT (Group.cu). AMD faults on double-free/default-constructed handles where CUDA tolerates. Confirm handles default-init to 0 and dtors are guarded (Texture.cu:69 sets textureObject=0 after destroy -- good pattern; audit the rest).
6. Device-function-pointer dispatch under HIP RDC (MED, Backend 1). The megakernel's whole correctness rests on `-rdc`/resolve-device-symbols linking the CH/AH/intersect pointers. cuBQL s07 proved function-pointer + hipMemcpyFromSymbol dispatch works on gfx90a; still the #1 thing to confirm at first run.
7. Fresh device memory not zeroed on ROCm (LOW-MED). Audit kernels writing sub-regions (the SBT/prims buffers are fully written; low risk).
8. `-ffp-contract=fast` default on hipcc vs nvcc expression-only (LOW). Ray/triangle intersection math (TraceInterface.h intersectTriangle) is tolerance-based, not bit-exact-gold-compared, so ULP drift is acceptable for an image renderer; pin `-ffp-contract=on` only if a reference-image compare proves too tight.
9. extended-lambda under hipcc (LOW). The cuda backend uses `[&,this]` device lambdas in traceRay; clang supports these; confirm they compile under the HIP pass.
10. OptiX-isms leaking outside rtcore/optix (LOW). grep confirmed OWL/optix symbols are confined to rtcore/optix + the optix barney instantiation; `barney/` host code talks only to the `rtc::` interface. The `BARNEY_RTC_OPTIX` dispatch in rtcore/*.h is additive (we add a `BARNEY_RTC_HIPRT` arm), no edit to the optix arm.
11. OptiX->HIPRT codegen fault class (HIGH, Backend 2 -- PRE-EMPT with EnvGS's proven workarounds). EnvGS hit a real register-pressure/JIT-scheduling fault class on ROCm 7.2.x hiprtc/comgr where heavy traversal kernels read stale values across the opaque traversal call. Apply these as EXPLICIT plan guidance to barney's hiprt trace kernel from the start, not after a failure:
    - Per-ray hit/payload records in GLOBAL scratch, NOT a kernel-stack array. Above a register-pressure threshold, writes the HIPRT filter makes to a stack-resident payload buffer become invisible to the caller; a global per-ray buffer (`params.chunk_buffer + tid*CHUNK_SIZE` in EnvGS) is pressure-immune. barney's per-ray hit list / any-hit accumulation must live in a global scratch buffer indexed by pixel/thread, not on the stack.
    - JIT/compile the trace kernel with `--gpu-max-threads-per-block=64` (EnvGS launches 8x8=64 and declares it, which relaxes the per-thread VGPR limit and fixes codegen). For barney's hipcc-native build the equivalent is `__launch_bounds__(64)` on the megakernel (or the matching launch-block declaration); set a small, declared block size for the trace kernel.
    - `__noinline__` + `__threadfence` around the traversal step. EnvGS made `traceStep` a `__noinline__` frame that returns the hit count and `__threadfence()`s after the traversal, so the heavy caller reads a fresh count and the filter's global writes are visible. Apply the same: keep barney's HIPRT traversal call in a small `__noinline__` helper that returns its result by value and fences before the caller reads shared/global hit state.
    - Reduce the backward/heavy-kernel register footprint: mark heavy device helpers `__noinline__` and read large inputs straight from global params rather than staging them into big local arrays. (barney's forward render is the analogue; if a gradient/backward path is ever added it inherits this.)
    Add a fault-class REVIEW STEP: when barney's hiprt hit/intersect programs first run, if outputs are stale/zero/NaN across the traversal boundary, apply these four before suspecting HIPRT itself.
12. The "Heisenbug" UB lesson -- AUDIT BEFORE BLAMING CODEGEN (HIGH-value, both backends). EnvGS's gfx90a NaN was first misdiagnosed as a ROCm hiprtc/comgr codegen miscompile; the ACTUAL root cause was UNDEFINED BEHAVIOR that nvcc happened to tolerate: (a) two value-returning `__device__` functions that fell off the end with NO return statement (the caller discarded the value on CUDA, so nvcc never miscompiled it; on HIP the path poisoned a surfel normal -> NaN gradients), and (b) a value used UNINITIALIZED on one branch (`cutoff` on the reflected bounce). Both are inlining-sensitive, giving the classic instrumentation-perturbs-it heisenbug profile. PLAN STEP (do this proactively): audit barney's `rtcore/cuda` AND `rtcore/hiprt` device programs (the 12 `*.dev.cu` CH/AH/intersect + the trace kernel) for (1) value-returning `__device__` functions with a control path that falls off the end, and (2) values read on some path before initialization -- BEFORE attributing any HIP/codegen discrepancy to the toolchain. Cheap mechanical check: compile the device TUs with `-Werror=return-type` (and review `-Wuninitialized`); the JIT does not surface these, so compile the kernel source yourself with the flag. This audit is fast and catches the most likely real fault.
