# cumm port plan

Planner: linux-gfx90a fleet job, 2026-11-25. Read-only analysis of upstream `d971d02a0` (v0.8.2+, 2026-03-21), pccm `860790f` (PyPI 0.4.16) and ccimport `f5af43d` (PyPI 0.4.4). Nothing was built and the fork was not touched. Inputs: the intake screen in `notes.md`, jeff's sizing study (`~/.claude/plans/moat-cumm-hip-backend-study.md`, a throwaway shim that built spconv's SIMT kernel set on gfx942 and found the walls listed below), and jeff's rulings of 2026-11-23.

## Project

- Name: cumm. Upstream https://github.com/FindDefinition/cumm, default branch `main`. Fork https://github.com/AMD-Ecosystem/cumm, port branch `moat-port`.
- What it is: "CUda Matrix Multiply". A Python package whose pccm meta-programs generate CUTLASS-style GEMM and implicit-GEMM convolution kernels (CUDA C++), plus `tensorview` (`tv::`), a header-only tensor and GPU-runtime layer, plus a small prebuilt pybind module `core_cc` (tensorview bindings, the NVRTC wrapper, `CompileInfo`). It is spconv's code generator: spconv generates and prebuilds its kernels with cumm at build time and JIT-compiles the rest through cumm's NVRTC layer at run time.
- Scope ruling (jeff, 2026-11-23, "Option B"): the port is complete only when an AMD matrix-instruction kernel family exists beside the plain (SIMT) kernels, MFMA on CDNA and WMMA on RDNA, for fp16 and bf16, as with Quest prefill. No pull request, review page or wheels before then. This plan therefore covers both the HIP backend and both matrix families; nothing is deferred and no partial-port question is open.
- Licence condition (clearance 2026-11-23): never modify the four GPL-3.0-or-later WITH GCC-exception-3.1 files `include/tensorview/core/nvrtc_std.h`, `core/nvrtc/core.h`, `core/nvrtc/limits.h`, `core/nvrtc/type_traits.h`. The hipRTC standard-library path goes into new files under the project's Apache-2.0 licence, written from scratch (do not copy from the GPL files or from libstdc++).
- Other rulings: work independently of ZJLi2013's FlyDSL rewrite and never use the package names `cumm-rocm`/`spconv-rocm` (use a per-ROCm-major name such as `cumm-rocm7`); ccimport is declined as already supported and is consumed unmodified from PyPI, which is a hard constraint on the build design below (pccm likewise is not ours to change).

## Existing AMD support

Improvable from nothing: there is no upstream HIP code (no `__HIP_PLATFORM`, `hip_runtime` or `__HIPCC_RTC__` anywhere in the tree), no upstream PR, issue or branch. `ZJLi2013/cumm-rocm` (branch `rocm`, dormant since 2026-05-09) is a community FlyDSL rewrite that replaces the codegen for gfx942 spconv inference; it is not authoritative, not a port of this code base, and jeff ruled to proceed independently. Not inherited.

Delivery vehicle: upstream does not link platform forks; it is a single-author repository that merges no outside PRs in practice (last outside merge 2022). Per the standing rule, the clean complete port is still offered as a PR after approval; the fork's `moat-port` and per-ROCm wheels are the real deliverable.

Mechanical port versus AMD-native rewrite: both, by component. The SIMT families and the runtime layer are a mechanical port (they are correct on gfx942 after small fixes, per the study). The NVIDIA tensor-core families (Volta `mma.sync.m8n8k4`, Turing/Ampere `mma.sync` + `ldmatrix`, Ampere `cp.async` multistage) have no HIP translation; they are excluded from HIP builds and replaced by new AMD-native families written against the compiler builtins `__builtin_amdgcn_mfma_*` and `__builtin_amdgcn_wmma_*` (the Quest precedent; no rocWMMA or Composable Kernel dependency, which also keeps hipRTC compiles self-contained).

## Build classification

Neither CMake nor a torch extension: a **pccm/ccimport code-generation build** driven by setuptools (`set-ext-type cumm pccm`). Evidence:
- `setup.py:170-189` builds `core_cc` with `pccm.extension.PCCMExtension` when `CUMM_DISABLE_JIT=1`; otherwise `cumm/__init__.py:29-38` builds it at import time with `pccm.builder.build_pybind` in an editable install.
- pccm writes a ninja file through ccimport; ccimport maps `.cu` to `nvcc` (`ccimport/buildtools/writer.py:880-902`) and keys compiler flags by logical compiler name (`nvcc`, `g++`, `clang++`, `cl`).
- No torch dependency (`setup.py` REQUIRED: pccm, pybind11, fire, numpy, sympy). CMake (`CMakeLists.txt`) only exports an INTERFACE target for downstream C++ users; nothing in cumm builds with it.
- CUDA vs CPU-only is decided by whether `nvcc --version` runs (`cumm/constants.py:48-58`).

## Port strategy

Strategy-A-shaped for a codegen build (the skill's "anything else" row): a real HIP build target at the flag level, CUDA spelling kept in the generated sources and headers, one compat header, and semantic fixes behind `__HIP_PLATFORM_AMD__`. No hipify at build time (the study's on-the-fly hipify mangled project includes and inserted device headers into host and RTC headers; it is not shippable).

1. **Toolchain selection, entirely inside cumm.** ccimport has a vestigial `hipcc` entry that cannot build (`create_build_rule` raises for it), and `CUDACXX=hipcc` fails because cumm's and ccimport's `nvcc`-keyed flags (`-Xcompiler`, `-gencode`, `-Xcudafe`, `--extended-lambda`) reach clang. The route that needs no ccimport or pccm change: map the `.cu` suffix to the logical compiler `clang++` (`suffix_to_compiler={".cu": "clang++"}`, accepted by `pccm.builder.build_pybind`, `pccm/builder/pybind.py:16-33`), bind `clang++` to ROCm's `amdclang++` through `CCIMPORT_COMPILER_LINKER_MAP` (`ccimport/constants.py:22-37`, honored on every OS, `writer.py:211-214`), and put `-x hip --offload-arch=<gfx> ...` in the `clang++` flag bucket. On Linux `.cc` stays on g++, so `clang++` flags reach only `.cu`. `PCCMExtension`/`PCCMBuild` do not forward `suffix_to_compiler` (`pccm/extension.py:22-90`), so `setup.py` gets a small cumm-owned `build_ext` that calls `build_pybind` itself on HIP, and `cumm/__init__.py:33-38` passes the same arguments on the JIT path. cumm exposes these kwargs and the env setting as one helper (for example `cumm.common.get_hip_build_kwargs()`) so that spconv's build uses the identical recipe.
2. **Backend detection.** `constants.py` gains a HIP probe (ROCm root from `ROCM_PATH`/`HIP_PATH`, `/opt/rocm`, then the pip `rocm-sdk` via `rocm-sdk path --root`; `hipconfig --version`) and a `CUMM_HIP_BUILD`-style flag beside `CUMM_CPU_ONLY_BUILD`; nvcc keeps priority when both exist unless HIP is requested explicitly (an env var), so a CUDA machine behaves exactly as today.
3. **Arch identity.** A `CUMM_HIP_ARCH_LIST` (gfx names, `all` = a fixed list: gfx90a, gfx942, gfx950, gfx1100, gfx1101, gfx1102, gfx1151, gfx1200, gfx1201; default: the local GPUs via `amdgpu-arch`/`rocm_agent_enumerator`, deduplicated) produces `--offload-arch` flags. CC tuples collide on AMD (gfx90a reports 9.0 = Hopper, gfx942 9.4), so on HIP `CompileInfo` compiles in the gfx names and `arch_is_compiled*`/`arch_is_compatible*` compare the device's `gcnArchName` (feature suffix stripped), `has_ptx` is always false (no forward-compatible IR), and a new binding returns the device arch name. `get_compute_capability` keeps returning HIP's major/minor for API compatibility but nothing in cumm selects kernels by it on HIP. Algorithm availability on HIP is by family string (Simt, SimtDP4A, the AMD families), never by `min_arch` tuple comparison: `cumm/gemm/algospec/core.py` gets a HIP-side availability helper keyed by gfx name that spconv can call (the spconv port then filters its descriptor lists through it).
4. **Compat header.** One new header (for example `include/tensorview/cuda/hip_compat.h`) with the runtime/driver aliases (`cuda*`->`hip*`, `CU*`->`hip*`, `CUdeviceptr`, error macros), cooperative groups, fp16/bf16 (`__nv_bfloat16` -> `__hip_bfloat16`), complex, curand -> hiprand, cublasLt -> hipblasLt, included under `__HIP_PLATFORM_AMD__` where the tensorview headers include CUDA headers today, and by the generator's `_CudaInclude`. It must be host-includable (g++/MSVC compile the generated `.cc` files against it) and skip `hip_runtime.h` under `__HIPCC_RTC__`.
5. **Semantic fixes** behind `__HIP_PLATFORM_AMD__` or `__HIP_DEVICE_COMPILE__` (list below), leaving every CUDA line as it is.
6. **hipRTC path** in new files: `cuda/hiprtc.h` (or a HIP branch inside `cuda/nvrtc.h`, keeping the `NVRTCProgram`/`NVRTCModule` class names the bindings and `gemm/core/nvrtc_bases.h` use), a HIP driver wrapper in place of `cuda/driver.h`'s libcuda dlopen, `core/rtc_std.h` as the new dispatcher that selects `core/hiprtc_std.h` under `__HIPCC_RTC__` and the untouched `nvrtc_std.h` otherwise, with the includers repointed.
7. **AMD matrix families** as new generator families (design below).

## AMD matrix-instruction families (the Option B work)

Goal: fp16 and bf16 GEMM and implicit-GEMM convolution kernels on AMD matrix hardware, with fp32 accumulation, output fp16/bf16/fp32 (the dtype combinations cumm's Turing family generates for f16 and bf16), every layout (`trans_a/b/c`), the shuffle (gather/scatter) variants spconv uses, split-K, and the conv input iterators (fwd, dgrad, wgrad; dense and sparse/mask). Two families, because the wavefront width changes the thread count of the block:

- **CDNA family (MFMA, wave64)**: gfx90a, gfx942, gfx950. Instructions `__builtin_amdgcn_mfma_f32_16x16x16f16` and `__builtin_amdgcn_mfma_f32_16x16x16bf16_1k` (both exist on all three; one code path; gfx950's 16x16x32 forms are a later tuning step). Operand layout as verified on the GPU for Quest: lane l, A row l%16 with k = 4(l/16)..+3; B column l%16, same k; D rows 4(l/16)+i, column l%16, i = 0..3.
- **RDNA family (WMMA, wave32)**: gfx11 (`__builtin_amdgcn_wmma_f32_16x16x16_{f16,bf16}_w32`, A/B hold all 16 k per lane with lanes 16-31 repeating 0-15; D rows 2i + l/16) and gfx12 (`..._w32_gfx12`, A/B k = 8(l/16)..+7; D rows 8(l/16)+i). One generated kernel, the two layouts selected per device pass by `__GFX11__`/`__GFX12__` inside the warp MMA, warp iterators and output fragment iterator.
- Naming: cumm names families after NVIDIA generations (`Volta`, `Turing`, `Ampere`); the new `GemmAlgo` values follow suit with neutral AMD names (porter's choice, for example `AmdMfma` and `AmdWmma`), each with its own `TensorOp` shape (16,16,16) so descriptors stay distinguishable, an entry in `_GEMM_MIN_ARCH_TO_ALGO` that a CUDA device can never satisfy, the `params.h:94` assertion, and both `ALGO_TO_SPEC` maps.

Design (smallest structure that reuses the most):
- **Warp = one wavefront.** The MFMA family's warp is 64 lanes, so `constants.WARP_SIZE` becomes a per-family value (prologue `lane_idx`/`warp_idx`, `num_threads = warp_count * warp_size` in `gemm/kernel.py:465`, `conv/kernel.py:575` and the algospecs). SIMT keeps its 32-lane logical warps; the WMMA family is 32 lanes and fits the existing plumbing.
- **Input side**: reuse the SIMT family's global-memory iterators and stripmined thread maps (they do not assert 32 lanes) and a pitch-linear shared-memory tile with padding against bank conflicts, instead of the Turing swizzled `TensorOpMultiplicand` layout (which exists for `ldmatrix`). Conv input iterators are shared across families and need only the new thread map.
- **New pieces per family**: a `WarpMma` (`bases.WarpMma`: fragments, device `operator()`, `min_arch`), warp iterators that load A/B fragments from LDS straight into the instruction's register layout (B for the transposed cases needs a strided 16-bit LDS read), an output fragment iterator and warp-store iterator matching the D layout, then reuse of `OutSmemLoader`/`OutIterator`/`LinearCombination`/`ApplyOutputOp` as the SIMT output does. Two-stage pipelining (`blockmma/mma.py`); no `cp.async` analogue (CDNA2 has none; synchronous global-to-LDS staging).
- **Python simulator**: the new classes need no `async __call__` simulation (cudasim is a visualisation aid; scoped out).
- **Parameter lists**: a tuned, small set per family (tile 64x64..128x128, warp tile 32x32/64x32 per wave, k 32), added to `GemmMainUnitTest`/`ConvMainUnitTest` gated to HIP, and exported so spconv can prebuild them.
- **Size**: 3,000 to 5,000 new generator lines across both families (new algospec + wmma + warp/out iterators for gemm and conv; the Turing family it replaces is about 5,500 lines, and the reuse of SIMT input and output stages is where the saving comes from).
- **Performance bar** (recorded evidence, not a pass/fail gate): fp16 and bf16 GEMM at 4096^3 and a spconv-shaped implicit GEMM (rows 1e6, C 64..256) against the SIMT family and against hipBLASLt on the same GPU; the matrix families must beat SIMT clearly (expect 4x or more on CDNA) and the plan records the hipBLASLt ratio. A matrix family slower than SIMT is a defect to fix, not to ship.

## Risk list

- **Compiler identity (highest, silent):** `defs.h:17` does not recognise hip-clang, so without the new branch every `TV_HOST_DEVICE_INLINE` is plain `inline` and device code fails or silently loses `__device__`. Fix it first; re-check that the HIP branch defines exactly what the nvcc branch does.
- **Wavefront width:** the 32-lane logical warp design survives wave64 only if every cross-lane op is width 32 (prologue broadcast, mask xor reductions, all of `parallel/ops.h`). The MFMA family is genuinely wave64 and must not inherit any 32-lane assumption (thread maps assert `prod == 32`; Turing fragment sizes divide by 32). Validate both widths on hardware.
- **Uninitialised-value UB** (`warp_res`): build the device code once with `-Wsometimes-uninitialized -Wconditional-uninitialized` and treat any device hit as a defect (the study found exactly one other, host-side, harmless).
- **Predicate semantics in the PTX replacements:** the PTX keeps the destination when the predicate is false; the commented C++ near `sparse_iters.py:303-305` writes 0. Keep the PTX semantics.
- **Fresh device allocations are not zeroed on ROCm**: audit `tv::empty` buffers whose first access is a read-modify-write (counters in hash/indices); the study's poisoned-allocator run found none in the spconv path, re-check the cumm-only paths (split-K semaphore workspace, `hash.cu.h` counters).
- **CC collision:** never select by CC on HIP (gfx90a reports 9.0, gfx942 9.4, gfx11 11.x); select by gcnArchName and family string. spconv's `min_arch` filtering is fixed in spconv, using the cumm helper.
- **Shared memory:** 64 KiB per block on all targets; configurations above it are dropped on HIP; RDNA's occupancy query answers wrongly above 64 KiB, so never use it as the fit test.
- **hipRTC is not NVRTC:** include spelling (`-I`, not `--include-path=`), no `-default-device`, host runtime headers absent (compat header must skip `hip_runtime.h` under `__HIPCC_RTC__`), macros from the host build are absent from the runtime compile unless passed (`-D__HIP_PLATFORM_AMD__` etc.), `-fgpu-rdc` gives empty code objects, the log must be NUL-terminated, Windows hipRTC DLL name carries the version, and Windows hipRTC rejects an absolute program name. The RTC std headers are the largest unknown: hipRTC predeclares some `std` traits and int typedefs, so expect clashes to resolve in `hiprtc_std.h`.
- **Licence boundary:** the four GPL files stay byte-identical (`git diff --stat` on them must be empty in every round); `hiprtc_std.h` must be written independently.
- **Windows toolchain:** MSVC compiles `.cc`, amdclang++ compiles `.cu` for the windows-msvc target. ccimport's default meta adds `-fPIC` for `clang++` on every OS (`writer.py:940`), which clang may reject for an msvc target, and cumm cannot remove a default flag without changing ccimport. First porter action on Windows: test it. If it fails, the options (a launcher in cumm that drops the flag, or a ccimport change, which would reopen jeff's "already supported" ruling) go to jeff. Also clang-cl/MSVC strictness in code that met only nvcc + cl, `uint128.h` `_umul128` in device code, and the DLL search.
- **FP contraction:** clang's default `-ffp-contract=fast` differs from nvcc builds; set tolerances per dtype in the harness (fp32 relative 1e-5, fp16/bf16 by K-scaled rounding), read error magnitudes rather than pass bits.
- **rocThrust spelling:** confirm whether `thrust::cuda::par` exists in rocThrust; otherwise branch to `thrust::hip::par`.
- **Package size and build time:** prebuilt kernel count times gfx count; cumm itself prebuilds only `core_cc` (no kernels), so this lands on spconv, but the gfx list policy is decided here.

CUMM_HIP_ARCH_LIST=<gfx> pip install -e . && python -c "import cumm.tensorview as tv; print(tv.is_cpu_only())"

## Test plan

Upstream has no assertion-bearing GPU tests for the kernels (CI runs none; the `main_real*` drivers print norms). The port ships a harness; the validator runs all of it.

GPU tests (every platform):
1. `pytest test/test_tensorview_gpu.py`: H2D/D2H round trips, pinned and managed memory, streams/events (`CUDAKernelTimer`), hash table insert/lookup with 32- and 64-bit keys and partially active waves (the `atomicAggInc` regression), block reduce, with a poisoned allocator pass.
2. `pytest test/test_gemm.py`: for each family available on the device (SIMT f32/f16, SimtDP4A s8, and the MFMA or WMMA family for f16 and bf16 with f16/bf16/f32 output), every `trans` combination, split-K, the shuffle (gather A/C, scatter) variants, odd sizes (M, N, K not multiples of the tile), compared to numpy fp64 references with dtype tolerances; run through both the prebuilt route (`build_pybind`, as spconv uses) and hipRTC (ConstantMemory, KernelAndCPU, Direct); assert DynamicParallism raises a clear error on HIP; assert that kernels actually dispatched (count launches or read the HIP runtime log once) so a green run cannot be an empty kernel.
3. `pytest test/test_conv.py`: implicit-GEMM conv fwd/dgrad/wgrad, dense 2D/3D and sparse-mask iterators, SIMT and the device's matrix family, against a numpy (or torch when present) reference.
4. Existing tests: `pytest test/test_tensors.py test/math test/reduce` (inliner through hipRTC; `test_array.py` imports numba, an optional test dependency) and `python test/cutest_nvrtc_std.py` (RTC std headers).
5. Performance record: `python -m` the benchmark entry the porter adds (or a pytest-benchmark-free script in `test/`), fp16/bf16 matrix family vs SIMT vs hipBLASLt; numbers to `notes.md`.

Non-GPU regression set: CPU-only install (no ROCm, no CUDA on PATH, or `CUMM_CUDA_VERSION=""`) imports and `tv.is_cpu_only()` is true; `test/math` CPU paths and `test_cpu_v0` (llvmlite) where llvmlite is installed; Python-side kernel generation for every family runs without a GPU; the CUDA generated-source diff above. Metal is not testable on the fleet; the diff must show no change under `__APPLE__`/`__METAL_VERSION__` branches.

Per gate:
- **wave64**: gfx90a (this class of host) or gfx942/gfx950. Items 1-5 with the MFMA family. Both gfx90a and gfx942 runs are wanted as evidence (bf16_1k MFMA and LDS behaviour are the same, but the CC collision differs: 9.0 vs 9.4).
- **wave32**: gfx1100 and gfx1201 (the two WMMA layouts are different code; a gfx11-only pass leaves the gfx12 layout unvalidated, so the gfx12 run is owed even after the gate is satisfied). Items 1-5 with the WMMA family.
- **windows**: windows-gfx1151, last, after both Linux widths pass at the same head. Items 1-4 (WMMA gfx11 layout, MSVC host + amdclang++ device, hipRTC DLL discovery); item 5 recorded but not compared to the Linux numbers (APU).
- **CUDA**: mi355 nvcc compile + generated-source diff, before any round is brought to jeff.

Downstream: spconv's own tests (pair generation vs CPU, SubMConv3d/SparseConv3d all algorithms fwd/bwd, fp32 and fp16/bf16 through the matrix families) belong to the spconv project and run against this port's head; they are the strongest end-to-end evidence that the cumm surface is complete and should be run once cumm reaches review-passed.

## Open questions

Not blocking the porter (the scope ruling settles the deliverable); recorded in `notes.md` for jeff:
1. int8 and tf32: cumm's NVIDIA tensor-op families also cover int8 (Turing/Ampere `imma`, spconv's int8 inference) and tf32. The ruling names fp16 and bf16, so this plan keeps int8 and tf32 GEMMs on the SIMT kernels on HIP (correct, slower). AMD has int8 matrix instructions on all targets (MFMA i8, WMMA iu8) and xf32 only on gfx942. Extending the families to int8 is a later decision.
2. SimtDP4A: optional `__builtin_amdgcn_sdot4`/`sudot4` acceleration of the int8 SIMT path (instruction availability differs by target and must be probed with `__has_builtin`); planned as off unless jeff wants it.
3. Windows `-fPIC` from ccimport's default flags for an msvc-target clang (see risks); answered by a test in the Windows round, and only then a question if it fails.
4. Wheel publication venue and gfx list for `cumm-rocm7` wheels (a person's decision, after the port is complete).
